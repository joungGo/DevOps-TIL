# 오토스케일링 — 스케일 다운의 목적과 미작동 시 결과

---

## 1. 오토스케일링의 목적 구조

클라우드의 핵심 가치는 **"쓴 만큼만 낸다"** 는 것이다. 오토스케일링은 이 가치를 실현하는 메커니즘이다.

|방향|트리거|목적|
|---|---|---|
|**스케일 업**|부하 증가|서비스 품질 유지 (응답 지연 방지)|
|**스케일 다운**|부하 감소|비용 절감 (안 쓰는 자원 반납)|

---

## 2. 온프레미스 vs 클라우드 오토스케일링

```
온프레미스 (서버 직접 구매):
  최대 트래픽 기준으로 서버를 미리 구매
  → 평소엔 서버가 놀고 있어도 비용은 고정
  → 트래픽이 예상을 초과하면 대응 방법 없음

클라우드 오토스케일링:
  트래픽 많을 때 → EC2 10대 → 비용 발생
  트래픽 없을 때 → EC2 2대  → 비용 절감
  → 트래픽 패턴에 따라 비용 자동 최적화
```

**스케일 다운을 안 하면 클라우드를 쓰는 의미가 없다.**  
항상 최대치를 유지하는 것은 온프레미스와 비용 구조가 동일해진다.

## 3. 실제 비용 차이 (현재 프로젝트 기준)

```
t3.medium 온디맨드: 약 $0.052/시간

스케일 다운 안 할 때 (Pod/Node 10개 상시 유지):
  $0.052 × 10대 × 24시간 × 30일 = $374.4/월

스케일 다운 할 때 (부하 1시간/일 가정):
  부하 중:  $0.052 × 10대 × 1시간        = $0.52
  평상시:   $0.052 × 2대  × 23시간       = $2.39
  1일 합계: $2.91 × 30일                 = $87.3/월

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
스케일 다운 유무만으로 월 $287 차이
```

## 4. 스케일 다운을 안 하면 발생하는 문제

### 문제 1. 비용 낭비

```
부하가 끝난 후에도 Pod 10개, Node 10개 유지
→ 아무 일도 안 하는 자원에 $299/월 지출
```

### 문제 2. NodePool 한도 소진 → 다음 부하 때 스케일 불가

```yaml
# nodepool.yaml
limits:
  cpu: "20"    # t3.medium 10개 = 20 vCPU = 이미 꽉 참
```

```
1차 부하: 노드 10개 생성 → 스케일 다운 안 함 → 10개 유지
2차 부하: Karpenter가 노드를 더 만들려 함
          → "CPU 한도 20 이미 도달, 생성 불가"
          → 새 Pod들 Pending 상태 누적
          → 서비스 응답 지연 / 503 에러 발생
```

### 문제 3. 한도 초과 시 서비스 장애

```
NodePool 한도 도달 이후 트래픽 계속 증가
  │
  ▼
새 Pod 스케줄 불가 → Pending 누적
  │
  ▼
기존 Pod들이 모든 요청 감당
  ├─ CPU throttling (limits 1000m 초과 불가)
  ├─ 응답 시간 급증 (1초 → 10초 → 타임아웃)
  ├─ 503 Service Unavailable
  └─ Pod OOM(메모리 초과) → 강제 종료 → 재시작 반복
```

## 5. 최종 정리

```
스케일 업   = 서비스 유지
스케일 다운 = 다음 스케일 업을 위한 여유 확보 + 비용 절감

둘 다 없으면 → 서비스 장애 + AWS 청구서 폭탄 동시 발생
```

|상황|결과|
|---|---|
|스케일 다운 비활성화|비용 낭비 + 한도 소진으로 다음 부하 대응 불가|
|부하가 한도 초과|503 에러, 응답 지연, Pod 강제 종료|
|한도도 없고 스케일 다운도 없음|AWS 청구서 폭탄|
