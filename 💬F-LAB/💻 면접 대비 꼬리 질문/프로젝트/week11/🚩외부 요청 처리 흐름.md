`week11` 문서 기준 권장 구조에서는 외부 요청이 이렇게 흐릅니다.

```text
Client
-> NLB
-> ingress-nginx Controller Service
-> ingress-nginx Controller Pod
-> Ingress rule
-> url-shortener Service
-> url-shortener API Pod
```

조금씩 풀면:

1. 사용자가 `api.bidflow.cloud`로 요청
- 브라우저나 `curl`이 `http://api.bidflow.cloud` 또는 `https://api.bidflow.cloud`로 요청합니다

2. DNS가 `api.bidflow.cloud`를 NLB로 해석
- Route53 레코드가 `api.bidflow.cloud`를 `ingress-nginx` 앞단 NLB로 연결합니다

3. 요청이 AWS NLB로 들어감
- `ingress-nginx-controller`의 `Service type=LoadBalancer` 앞에 붙은 NLB가 외부 요청을 받습니다
- `week11` 권장 경로에서는 NLB는 L4 전달만 하고, TLS 종료는 nginx 쪽에서 하게 설계합니다

4. NLB가 `ingress-nginx-controller Service`로 전달
- 80/443 포트 요청이 `ingress-nginx-controller` Service로 들어갑니다

5. Service가 `ingress-nginx-controller Pod`로 전달
- Service selector가 controller Pod를 찾아서 트래픽을 넘깁니다
- replica가 2개면 둘 중 하나의 Pod가 받습니다

6. `ingress-nginx`가 TLS 종료 + L7 정책 처리
- HTTPS 요청이면 여기서 TLS 종료
- HTTP 요청이면 `force-ssl-redirect`, `ssl-redirect` annotation에 따라 HTTPS로 리다이렉트
- 이후 host/path, rate limit, allow/deny 같은 nginx annotation 정책을 적용합니다

7. Ingress rule을 보고 backend 결정
- `host: api.bidflow.cloud`
- `path: /`
이 조건에 맞으면 `url-shortener-svc`로 보냅니다

8. `url-shortener Service`로 전달
- `ClusterIP` Service가 backend 역할을 합니다

9. Service가 실제 `url-shortener-api Pod`로 전달
- Service selector에 맞는 FastAPI Pod 중 하나가 요청을 처리합니다

10. Pod 내부에서 애플리케이션 처리
- 읽기 요청은 RDS Replica를 사용할 수 있고
- 쓰기 요청은 RDS Primary를 사용
- 캐시 조회는 Redis를 사용합니다

요약하면 핵심 역할 분리는 이렇습니다.

- `Route53`: 도메인 -> NLB 연결
- `NLB`: 외부 진입점
- `ingress-nginx`: TLS 종료 + HTTP/HTTPS redirect + L7 정책 + 라우팅
- `url-shortener Service`: 앱 Pod로 전달
- `url-shortener Pod`: 실제 비즈니스 처리

한 줄로 제일 짧게 말하면:
- **외부 요청은 NLB를 거쳐 ingress-nginx에서 TLS/정책 처리를 받고, 그 다음 url-shortener Service를 통해 API Pod까지 전달됩니다.**
