`Gateway API`는 Kubernetes에서 `Ingress`를 더 확장하고 구조화해서 만든 차세대 트래픽 관리 API입니다.

쉽게 말하면:
- `Ingress`보다 더 유연하고
- 역할 분리가 잘 되어 있고
- HTTP뿐 아니라 TCP, TLS 같은 다양한 트래픽까지 더 잘 다룰 수 있게 만든 표준입니다

기존 `Ingress`가 대체로
- “외부 요청을 어느 Service로 보낼까”
정도에 집중했다면,

`Gateway API`는
- 누가 진입점을 소유하는지
- 어떤 팀이 라우팅 규칙을 관리하는지
- 어떤 Listener(80, 443, TLS)를 열지
- 어떤 Route를 어느 Gateway에 붙일지

이런 걸 더 명확하게 나눕니다.

핵심 리소스는 보통 이렇습니다.

- `GatewayClass`
  클러스터에서 어떤 종류의 Gateway 구현체를 쓸지 정의
- `Gateway`
  실제 진입점. 예: 80/443 포트를 열고 어떤 프로토콜을 받을지 정의
- `HTTPRoute`
  HTTP 요청을 어떤 규칙으로 어디에 보낼지 정의
- `TCPRoute`, `TLSRoute` 같은 다른 Route
  HTTP 외 트래픽 처리용

비유하면:
- `Ingress`는 “출입문 규칙을 한 장에 다 적는 방식”
- `Gateway API`는 “건물 출입문, 경비 정책, 방문자 동선 규칙을 역할별로 나눠 적는 방식”

왜 쓰냐면:
- `Ingress`보다 표현력이 좋음
- 멀티팀 운영에 유리함
- 클라우드/벤더 구현체가 더 일관되게 확장 가능함
- 장기적으로 Kubernetes 네트워킹 표준 방향에 가까움

하지만 단점도 있습니다.
- `Ingress`보다 개념이 많아서 처음엔 어렵습니다
- 지금 프로젝트처럼 단순한 실습에는 오히려 과할 수 있습니다
- 컨트롤러가 Gateway API를 지원해야 합니다

한 줄 요약:
`Gateway API는 Ingress보다 더 유연하고 역할 분리가 잘 된, Kubernetes의 차세대 트래픽 관리 표준입니다.`

> [!NOTE] Ingress vs Gateway API 구조 차이
> 
> `Ingress`도 겉으로 보면
> 
> - 진입 처리: `ingress-nginx-controller`
>     
> - 라우팅 규칙: `Ingress`  
>     처럼 분리돼 보입니다.
>     
> 
> 하지만 `Gateway API`는 그 분리를 **리소스 모델 차원에서 더 명시적으로** 합니다.
> 
> ---
> 
> ### Ingress 구조
> 
> 보통 한 `Ingress` 리소스 안에
> 
> - 어떤 호스트를 받을지
>     
> - 어떤 경로를 받을지
>     
> - 어느 서비스로 보낼지
>     
> 
> 가 같이 들어갑니다.
> 
> 👉 즉, “진입점 설정”과 “라우팅 규칙”이 논리적으로 섞여 있는 구조입니다.
> 
> ---
> 
> ### Gateway API 구조
> 
> 리소스가 아예 나뉩니다.
> 
> - `Gateway`
>     
>     - 어떤 포트/프로토콜/리스너를 열지
>         
>     - 누가 이 진입점을 소유하는지
>         
> - `HTTPRoute`
>     
>     - 어떤 host/path 요청을 어디로 보낼지
>         
> 
> 👉 즉,
> 
> - 플랫폼 팀 → `Gateway` 관리
>     
> - 애플리케이션 팀 → `HTTPRoute` 관리
>     
> 
> 처럼 **권한과 책임 분리**가 자연스럽습니다.
> 
> ---
> 
> ### 정리
> 
> `Ingress`도 어느 정도 분리된 것처럼 보이지만,  
> `Gateway API`는 진입점과 라우팅 규칙을 **리소스 수준에서 더 명확하고 엄격하게 분리**합니다.
> 
> ---
> 
> ### 한 줄 요약
> 
> 👉 _Ingress는 논리적 분리, Gateway API는 구조적(리소스 수준) 분리_
