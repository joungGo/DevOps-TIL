### 답변
멀티프로세싱 환경에서는 프로세스 간 주소 공간이 분리되어 있기 때문에  
IPC 방식에 따라 **성능과 안정성 특성**이 달라집니다.

먼저, **파이프(Pipe)** 입니다.  
커널 버퍼를 통해 단방향으로 데이터를 전달합니다.  
구현이 단순하고 안정적이지만,  
커널을 반드시 거치므로 복사 비용이 발생합니다.  
부모-자식 관계에서 주로 사용됩니다.

다음은 **소켓(Socket)** 입니다.  
로컬 또는 네트워크 기반 통신이 가능합니다.  
유연성과 확장성이 높지만,  
프로토콜 스택을 거치기 때문에 오버헤드가 가장 큽니다.  
분산 시스템이나 프로세스 간 느슨한 결합에 적합합니다.

세 번째는 **메시지 큐(Message Queue)** 입니다.  
커널이 메시지 단위로 관리합니다.  
비동기 통신이 가능하고 구조화된 데이터 전달에 유리합니다.  
하지만 역시 커널 개입이 필요해 컨텍스트 스위칭 비용이 존재합니다.

마지막으로 **공유 메모리(Shared Memory)** 입니다.  
여러 프로세스가 동일한 물리 메모리를 직접 매핑합니다.  
커널 개입 없이 접근하므로 가장 빠른 IPC 방식입니다.  
하지만 동기화를 직접 구현해야 하므로  
레이스 컨디션이나 데이터 손상 위험이 있습니다.

정리하면,

- 공유 메모리: 최고 성능, 낮은 격리
    
- 파이프/메시지 큐: 중간 성능, 커널 관리로 안정성 높음
    
- 소켓: 가장 높은 오버헤드, 대신 네트워크 확장성과 유연성 제공
    

즉,  
성능을 우선하면 공유 메모리,  
안정성과 확장성을 우선하면 메시지 기반 IPC를 선택하는 구조라고 설명할 수 있습니다.

### 꼬리질문: 각 IPC 방식을 사용하는 실제 사례를 들어서 설명해보세요.
각 IPC 방식은 사용 목적에 따라 실제 시스템에서 다르게 활용됩니다.

먼저, **파이프(Pipe)** 입니다.  
대표적인 예는 리눅스 쉘에서의 `|` 연산자입니다.  
예를 들어 `ps aux | grep nginx`와 같이  
한 프로세스의 출력을 다른 프로세스의 입력으로 연결할 때 사용됩니다.  
부모-자식 프로세스 간 단순 스트림 전달에 적합합니다.

다음은 **소켓(Socket)** 입니다.  
웹 서버와 애플리케이션 서버 간 통신,  
또는 마이크로서비스 간 REST/gRPC 통신이 대표적인 사례입니다.  
로컬 통신에서는 Unix Domain Socket을 사용해  
TCP보다 낮은 오버헤드로 통신하기도 합니다.

세 번째는 **메시지 큐(Message Queue)** 입니다.  
예를 들어 백엔드 시스템에서  
주문 서비스가 결제 서비스로 이벤트를 전달할 때  
RabbitMQ나 Kafka 같은 메시지 브로커를 사용합니다.  
비동기 처리와 장애 격리에 유리합니다.

마지막으로 **공유 메모리(Shared Memory)** 입니다.  
데이터베이스 시스템에서  
여러 워커 프로세스가 버퍼 캐시를 공유할 때 사용됩니다.  
또는 고성능 멀티프로세스 서버에서  
대용량 데이터를 빠르게 교환해야 할 때 활용됩니다.

정리하면,

- 파이프: 단순 스트림 연결, 쉘 파이프라인
    
- 소켓: 네트워크 기반 서비스 간 통신
    
- 메시지 큐: 비동기 이벤트 기반 시스템
    
- 공유 메모리: 고성능, 대용량 데이터 교환
    

즉, 결합도와 성능 요구 수준에 따라 IPC 방식을 선택합니다.

### 꼬리질문: 각 IPC 방식의 보안적 측면에서 어떠한 고려사항이 있을까요?
#### 1. Pipe (파이프)

**보안 특성**

- 기본적으로 부모-자식 관계에서만 사용
    
- 파일 디스크립터 기반 접근 제어
    

**보안 고려사항**

- 파일 디스크립터 상속 관리 필요 (`close-on-exec`)
    
- 잘못된 권한 설정 시 의도치 않은 프로세스가 접근 가능
    
- 입력값 검증 미흡 시 command injection 가능성
    

**보안 수준**

- 상대적으로 안전 (사용 범위가 제한적)
    
- 로컬 프로세스 내부 통신에 적합
    

---

#### 2. Socket (소켓)

**보안 특성**

- 로컬 또는 네트워크 기반 통신 가능
    
- 가장 넓은 공격 표면
    

**보안 고려사항**

- 인증(Authentication) 필요 (TLS, mutual TLS 등)
    
- 암호화(Encryption) 적용 필요
    
- 포트 노출 관리 (방화벽, 보안 그룹)
    
- DoS 공격 가능성
    
- Unix Domain Socket의 경우 파일 권한 관리 중요
    

**보안 수준**

- 네트워크 노출 시 가장 위험
    
- 적절한 암호화 및 인증이 필수
    

---

#### 3. Message Queue (메시지 큐)

**보안 특성**

- 브로커 기반 구조
    
- 비동기 메시지 전달
    

**보안 고려사항**

- 브로커 접근 제어 (ACL)
    
- 토픽/큐 권한 분리
    
- 메시지 암호화
    
- 메시지 위변조 방지
    
- 메시지 재전송 공격(replay attack) 방지
    

**보안 수준**

- 중앙 브로커가 단일 장애 지점이자 공격 지점
    
- 인증/권한 설계가 핵심
    

---

#### 4. Shared Memory (공유 메모리)

**보안 특성**

- 가장 빠르지만 가장 낮은 격리 수준
    

**보안 고려사항**

- 접근 권한 설정 (`shmctl`, `mmap` 권한)
    
- 메모리 데이터 노출 위험
    
- 프로세스 크래시 시 민감 정보 잔존 가능성
    
- 동기화 오류로 인한 데이터 손상
    

**보안 수준**

- 성능은 최고, 보안 통제는 가장 어려움
    
- 민감 데이터 처리 시 매우 신중해야 함
    

---

#### 종합 비교

|IPC 방식|공격 표면|인증 필요성|암호화 필요성|격리 수준|
|---|---|---|---|---|
|Pipe|낮음|거의 없음|불필요|높음|
|Socket|높음|필수|필수(네트워크)|낮음|
|Message Queue|중간|필수|권장|중간|
|Shared Memory|낮음(로컬)|OS 권한 의존|없음|매우 낮음|

---

결론적으로,

- 네트워크를 통과하는 IPC는 반드시 암호화와 인증이 필요
    
- 커널을 통한 IPC는 권한 관리가 핵심
    
- 공유 메모리는 성능은 좋지만 보안 통제가 가장 어렵기 때문에 민감 데이터에는 신중히 사용해야 함
    

즉, IPC 선택 시 **성능뿐 아니라 공격 표면과 격리 수준을 함께 고려해야 한다**는 점이 중요합니다.
