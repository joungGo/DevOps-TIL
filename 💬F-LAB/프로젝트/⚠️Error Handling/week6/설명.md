### 2. eks_addon을 resource로 따로 분리해야 하는 이유

```terraform
# EBS CSI Driver IRSA — terraform-aws-modules/iam 서브모듈 사용  
module "ebs_csi_irsa" {  
  source  = "terraform-aws-modules/iam/aws//modules/iam-role-for-service-accounts-eks"  
  version = "~> 5.0"  
  
  role_name = "${var.project_name}-ebs-csi-role"  
  
  # EBS CSI 전용 관리형 정책 자동 연결  
  attach_ebs_csi_policy = true  
  
  oidc_providers = {  
    main = {  
      provider_arn               = module.eks.oidc_provider_arn  
      namespace_service_accounts = ["kube-system:ebs-csi-controller-sa"]  
    }  
  }  
}  
  
# EKS Addon 등록 — 직접 리소스 유지 (모듈과 순환 의존성 방지)  
resource "aws_eks_addon" "ebs_csi" {  
  cluster_name             = module.eks.cluster_name  
  addon_name               = "aws-ebs-csi-driver"  
  service_account_role_arn = module.ebs_csi_irsa.iam_role_arn  
  
  tags = {  
    Name = "${var.project_name}-ebs-csi"  
  }  
}
```

#### 왜 EKS 모듈의 `cluster_addons`에 넣지 않는가

```hcl
# ❌ 이렇게 하면 순환 의존성 발생
module "eks" {
  cluster_addons = {
    aws-ebs-csi-driver = {
      service_account_role_arn = module.ebs_csi_irsa.iam_role_arn
      # module.ebs_csi_irsa 는 module.eks.oidc_provider_arn 을 필요로 함
      # module.eks 는 module.ebs_csi_irsa 를 필요로 함
      # → 서로가 서로를 기다리는 교착상태
    }
  }
}
```

```
module.eks
  → module.ebs_csi_irsa 필요
    → module.eks.oidc_provider_arn 필요
      → module.eks 필요  ← 무한루프
```

그래서 addon 등록을 별도 `resource "aws_eks_addon"`으로 분리하면:

```
1. module.eks 생성 완료 (OIDC Provider 포함)
      ↓
2. module.ebs_csi_irsa 생성 (module.eks.oidc_provider_arn 사용)
      ↓
3. aws_eks_addon 생성 (module.ebs_csi_irsa.iam_role_arn 사용)
```

순서가 명확해져서 순환 의존성이 해결됩니다.

> module.xxx.yyy 형태는 output.tf에서 참조하는 거라고 생각하면 됨
