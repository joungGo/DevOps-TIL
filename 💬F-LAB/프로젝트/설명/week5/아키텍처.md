## ALB가 두 AZ에 걸쳐 생성되는 이유

ALB는 생성 시 각 AZ의 Public Subnet에 **ALB 노드(내부 EC2)**를 하나씩 배치합니다. 이 노드들이 실제로 트래픽을 받아서 분산하는 주체입니다. AZ-a Public Subnet에 ALB 노드 하나, AZ-c Public Subnet에 ALB 노드 하나, 이렇게 두 개가 생깁니다.

이렇게 하는 이유는 단순합니다. **AZ-a 전체가 장애나면 AZ-c의 ALB 노드가 혼자 트래픽을 받아야 하기 때문**입니다. ALB 노드가 AZ-c에 없다면 AZ-a 장애 시 서비스 자체가 불가능해집니다. 여기서 `kubernetes.io/role/elb = 1` 태그가 중요한데, 이 태그가 붙은 Public Subnet에만 ALB 노드가 배치됩니다. Week4 Terraform 코드에서 Public Subnet에 이 태그를 달았던 이유가 바로 이겁니다.

---

## 트래픽 분산 방식 — 두 단계로 나뉩니다

**1단계 — DNS 라운드로빈 (사용자 → ALB 노드)**

ALB의 DNS 이름(`xxx.ap-northeast-2.elb.amazonaws.com`)은 AZ-a ALB 노드 IP와 AZ-c ALB 노드 IP를 번갈아 반환합니다. 사용자 A는 AZ-a 노드로, 사용자 B는 AZ-c 노드로 붙는 식입니다.

**2단계 — ALB 내부 로드밸런싱 (ALB 노드 → Worker Node)**

ALB 노드는 Listener Rule로 요청을 분류한 뒤 Target Group에 등록된 Worker Node들로 분산합니다. 이때 기본 알고리즘은 라운드로빈이지만, `least_outstanding_requests`(미처리 요청이 가장 적은 노드 우선)로 바꿀 수 있습니다.

여기서 중요한 설정이 `target-type`입니다.

```
target-type: instance  # NodePort로 전달 (기본값)
target-type: ip        # Pod IP로 직접 전달 (권장)
```

`instance` 모드에서는 ALB → Node의 NodePort → iptables DNAT → Pod 순서로 2홉이 발생합니다. `ip` 모드에서는 ALB가 Pod IP를 직접 알고 있어서 1홉으로 끝납니다. 이때 aws-load-balancer-controller가 K8s Endpoints를 감시하다가 Pod가 생성/삭제될 때마다 ALB Target Group을 자동으로 갱신합니다.

## 면접에서 자주 나오는 포인트

"ALB가 AZ-a에만 있는 Worker Node로 트래픽을 보낼 수 있나?"라는 질문이 있습니다. 답은 **yes이지만 Cross-AZ 비용이 발생합니다**. AZ-c의 ALB 노드가 AZ-a의 Worker Node로 트래픽을 보내면 AZ 간 데이터 전송 요금($0.01/GB)이 붙습니다. 이를 최소화하려면 `aws-load-balancer-controller`의 `target-type: ip` + `topology-aware routing` 조합으로 같은 AZ 내 Pod를 우선 선택하도록 설정합니다.

> [!info] Cross-Zone Load Balancing 핵심
> - ALB는 **Cross-Zone Load Balancing 기본 활성화**
> - Target Group의 Node를 **AZ 구분 없이 하나의 목록으로 인식**
> - 결과: ALB가 **라운드로빈으로 AZ 상관없이 분배**
>
> 예시:
> - Node-1 (AZ-a)
> - Node-2 (AZ-c)
> → AZ-a ALB도 [Node-1, Node-2] 둘 다로 전송
> → AZ-c ALB도 [Node-1, Node-2] 둘 다로 전송

> [!question] 왜 같은 AZ로만 보내지 않나?
> - Cross-Zone을 끄면 **같은 AZ로만 전송 가능**
>
> Cross-Zone OFF:
> - AZ-a ALB → AZ-a Node만
> - AZ-c ALB → AZ-c Node만
>
> → 네트워크 효율은 좋아짐

> [!warning] Cross-Zone OFF 문제점
> - 같은 AZ Node 장애 시 **트래픽 처리 불가**
> - 다른 AZ는 정상이어도 **우회 불가능**
>
> Cross-Zone ON:
> - 다른 AZ로 자동 우회 → 고가용성
>
> Cross-Zone OFF:
> - 같은 AZ 트래픽 실패

> [!summary] Cross-Zone ON vs OFF
> | | Cross-Zone ON | Cross-Zone OFF |
> |---|---|---|
> | 분산 | 모든 AZ 균등 분배 | 같은 AZ만 |
> | 장애 대응 | 다른 AZ 우회 | 실패 |
> | 비용 | Cross-AZ 비용 발생 | 비용 없음 |
> | 사용 | 기본값 (프로덕션) | 비용 최적화 |

> [!tip] 실무 타협 전략
> - 평상시: 같은 AZ 우선
> - 부족 시: 다른 AZ overflow
> - 이유: **비용 + 고가용성 균형**

> [!info] ALB 생성 흐름 (aws-load-balancer-controller)
> - ALB는 AWS가 미리 생성하지 않음
> - **Ingress 생성 시점에 aws-load-balancer-controller가 AWS API 호출하여 생성**
>
> ```
> Ingress 없음
> → ALB 존재하지 않음
> → Public Subnet에 ALB 노드 없음
>
> Ingress 생성
> → aws-load-balancer-controller 감지
> → AWS API로 ALB 생성 요청
> → 태그 달린 Public Subnet 스캔
>    (kubernetes.io/role/elb = 1)
> → AZ-a Public Subnet에 ALB 노드 1개 배치
> → AZ-c Public Subnet에 ALB 노드 1개 배치
> ```
