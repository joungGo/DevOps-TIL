### 2. eks_addon을 resource로 따로 분리해야 하는 이유

```terraform
# EBS CSI Driver IRSA — terraform-aws-modules/iam 서브모듈 사용  
module "ebs_csi_irsa" {  
  source  = "terraform-aws-modules/iam/aws//modules/iam-role-for-service-accounts-eks"  
  version = "~> 5.0"  
  
  role_name = "${var.project_name}-ebs-csi-role"  
  
  # EBS CSI 전용 관리형 정책 자동 연결  
  attach_ebs_csi_policy = true  
  
  oidc_providers = {  
    main = {  
      provider_arn               = module.eks.oidc_provider_arn  
      namespace_service_accounts = ["kube-system:ebs-csi-controller-sa"]  
    }  
  }  
}  
  
# EKS Addon 등록 — 직접 리소스 유지 (모듈과 순환 의존성 방지)  
resource "aws_eks_addon" "ebs_csi" {  
  cluster_name             = module.eks.cluster_name  
  addon_name               = "aws-ebs-csi-driver"  
  service_account_role_arn = module.ebs_csi_irsa.iam_role_arn  
  
  tags = {  
    Name = "${var.project_name}-ebs-csi"  
  }  
}
```

#### 왜 EKS 모듈의 `cluster_addons`에 넣지 않는가

```hcl
# ❌ 이렇게 하면 순환 의존성 발생
module "eks" {
  cluster_addons = {
    aws-ebs-csi-driver = {
      service_account_role_arn = module.ebs_csi_irsa.iam_role_arn
      # module.ebs_csi_irsa 는 module.eks.oidc_provider_arn 을 필요로 함
      # module.eks 는 module.ebs_csi_irsa 를 필요로 함
      # → 서로가 서로를 기다리는 교착상태
    }
  }
}
```

```
module.eks
  → module.ebs_csi_irsa 필요
    → module.eks.oidc_provider_arn 필요
      → module.eks 필요  ← 무한루프
```

그래서 addon 등록을 별도 `resource "aws_eks_addon"`으로 분리하면:

```
1. module.eks 생성 완료 (OIDC Provider 포함)
      ↓
2. module.ebs_csi_irsa 생성 (module.eks.oidc_provider_arn 사용)
      ↓
3. aws_eks_addon 생성 (module.ebs_csi_irsa.iam_role_arn 사용)
```

순서가 명확해져서 순환 의존성이 해결됩니다.

> module.xxx.yyy 형태는 output.tf에서 참조하는 거라고 생각하면 됨

### 3. Github이 AWS 리소스에 접근하기 위한 권한을 주는 방법

#### 방법1

```
(docker login 기반)

GitHub Actions
  └─ AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY (GitHub Secrets 저장)
  └─ aws ecr get-login-password → ECR 임시 토큰 발급
  └─ docker login --username AWS --password <토큰>
  └─ docker push → ECR
```

#### 방법2

```
현재 구현 방식 (OIDC 기반)

GitHub Actions
  └─ OIDC 토큰 발급 (GitHub 발급)
  └─ AWS STS에 제출 → IAM Role Assume
  └─ 임시 AWS 자격증명 발급
  └─ aws ecr get-login-password → ECR 임시 토큰 발급
  └─ docker login --username AWS --password <토큰>
  └─ docker push → ECR
```

> 결국 차이는, AWS Credential을 얻기 위한 방법(Access Key vs OIDC) 뿐임

> [!note] Docker는 왜 있을까?
> 
> ECR은 컨테이너 이미지를 저장하고 관리하는 레지스트리다. 이 이미지를 만들고 보내주는 도구가 Docker이고, GitHub에서 ECR까지 이미지를 넘기기 위해 거쳐야 하는 레이어가 크게 2가지 존재한다.
> 
> ```
> IAM Role (AWS 레이어)
>   └─ AWS API 호출 권한
>   └─ AWS Signature V4 방식으로 인증
>   └─ AWS CLI, SDK가 이해하는 방식
> 
> Docker CLI (Docker 레이어)
>   └─ 컨테이너 이미지 push/pull
>   └─ Docker Registry 프로토콜로 통신
>   └─ username/password(token) 방식으로 인증
>   └─ IAM을 모름
> ```
> 
> OIDC 토큰을 생성해서 AWS STS에 보내 검증받고 임시 AWS Credential을 얻는 과정은 AWS 레이어의 문을 여는 것과 같다. 이 문을 따기 위한 키가 `aws ecr get-login-password` 명령어로 발급받은 임시 토큰이다.
> 
> 문제는 Docker CLI가 AWS 레이어를 모른다는 점이다. Docker는 독자적인 Registry 프로토콜로 동작하기 때문에 IAM이나 AWS 자격증명을 이해하지 못한다. 그래서 발급받은 임시 토큰으로 `docker login`을 수행해 두 레이어 사이에 통로를 열어줘야 한다. 이 통로가 생긴 후에야 Docker가 ECR 주소를 인식하고 이미지를 push할 수 있다.

### Helm으로 ALB Controller 설치하기

```bash
# eks-charts 레포 추가
helm repo add eks https://aws.github.io/eks-charts
helm repo update

# ALB Controller 설치 변수 설정
CLUSTER_NAME=urlshortener
ALB_ROLE_ARN=$(cd terraform && terraform output -raw alb_controller_role_arn)
AWS_REGION=ap-northeast-2
AWS_ACCOUNT_ID=716174522908  # 실제 계정 ID로 변경

aws eks update-kubeconfig --region ap-northeast-2 --name urlshortener

helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  --namespace kube-system \
  --set clusterName=${CLUSTER_NAME} \
  --set serviceAccount.create=true \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set "serviceAccount.annotations.eks\.amazonaws\.com/role-arn=${ALB_ROLE_ARN}" \
  --set region=${AWS_REGION} \
  --set vpcId=$(cd terraform && terraform output -raw vpc_id) \
  --set crds.create=true \
  --version 1.8.1
```

### Helm 으로 ArgoCD 

전제
```bash
# 네임스페이스 생성
kubectl create namespace argocd

# ArgoCD 설치
helm repo add argo https://argoproj.github.io/argo-helm
helm repo update

helm install argocd argo/argo-cd \
  --namespace argocd \
  --set server.extraArgs[0]="--insecure"

# 설치 확인
kubectl get pods -n argocd
```

```bash
# argocd-server를 HTTP 모드로 전환
# (ALB에서 SSL termination을 처리하므로 argocd 내부는 HTTP로 동작)

# ✅ 방법 1: Helm upgrade — ArgoCD가 Helm으로 설치된 경우 권장
# --reuse-values: 기존 설정을 유지하면서 해당 값만 변경
helm upgrade argocd argo/argo-cd \
  --namespace argocd \
  --reuse-values \
  --set "configs.params.server\.insecure=true"

# 방법 2: kubectl patch — Helm 외 방식으로 설치된 경우
# ⚠️ 주의: args 배열이 초기화되어 있지 않으면 실패할 수 있음
# kubectl patch deployment argocd-server \
#   -n argocd \
#   --type='json' \
#   -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--insecure"}]'

# ArgoCD Ingress 적용
kubectl apply -f url-shortener/k8s/argocd/argocd-ingress.yaml
```
