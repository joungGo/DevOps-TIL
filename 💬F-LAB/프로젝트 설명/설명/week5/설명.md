## 전체 배포 흐름

```
개발자가 main 브랜치에 코드 Push
  ↓
GitHub Actions (CI) 자동 실행

  ├── 1. Lint / Unit Test 통과 확인

  ├── 2. Docker Multi-stage Build

  ├── 3. ECR Push (태그: git SHA)   예: abc1234

  └── 4. GitOps repo의 values.yaml tag 자동 업데이트 → git commit/push
  ↓
ArgoCD (EKS 내부) — 3분 주기 폴링 또는 Webhook

  └── OutOfSync 감지 → Auto Sync 실행
  ↓
EKS — Rolling Update 시작

  └── 노드가 ECR에서 새 이미지 pull → Pod 교체 완료
  ↓
ArgoCD Application 상태: Healthy / Synced
```

## 작업 순서

### 1. ECR Repo 생성

```tf
image_tag_mutability = IMMUTABLE # 한 번 push 한 태그는 변경 불가
```

이유 :
MUTABLE이면 v.1.0.0 이라는 태그가 오늘과 어제 다른 이미지를 가리킬 수 있음.
장애 발생 시 **어떤 코드가 배포됐는지 추적이 불가능함**

보통 `IMMUTABLE + Git SHA` 태그 조합으로 많이 사용

#### 1-1. ECR - Lifecycle Policy 설정해야 함

- ECR Storage Cost: $0.10/GB/월
- 목적: 비용 절감
- 보통 최신 `30~40개 이미지를 유지 + untagged 이미지 0일 후 삭제`

#### 1-2. 이미지 데이터 암호화 진행

방법 2가지
1. `encryption_type = "AES256"`
2. `encryption_type = "KMS"`

- **접근 제어 대상(사용자)가 없어서 AES256 사용**

#### 1-3. force_delete = false

`force_delete = false` 는 이미지가 있으면 terraform destory가 실패함.
운영환경에서는 실수를 방지하기 위해 false를 사용한다고 함. 하지만 나는 학습이니까 truef로 설정

### 2. Docker 빌드 & ECR Push

#### 2-1. Git SHA 태그 사용

- 이미지와 코드가 1:1로 대응됨
- CI가 자동으로 생성하므로 개발자가 개입할 필요가 없음
- 보통 IMMUTABLE + Git SHA 조합을 많이 사용함

#### 2-2. Multi-stage Dockerfile

- 이미지가 크면 ECR에서 pull 하는 시간이 증가함
- ECR Storage 비용이 증가함

**위 문제를 해결하기 위해 `빌드 단계`와 `실행 단계`를 분리하여 Dockerfile을 작성.**
= 최종 이미지에는 실행에 필요한 파일만 포함됨

Dockerfile 이미지 빌드 시간 및 네트워크 사용량 감소 고려

```dockerfile
# 개선 전
RUN pip install --no-cache-dir -r requirements.txt

# 개선 후
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --no-cache-dir --target=/install -r requirements.txt
```

- **BuildKit 전용 문법**(Docker BuildKit 활성화 필요: `DOCKER_BUILDKIT=1 docker build ...` 또는 CI 설정).
- 동작: 빌드 컨테이너의 `/root/.cache/pip` 경로를 "캐시 볼륨"으로 마운트.
    - 첫 빌드: pip가 패키지(whl/tarball)를 다운로드해서 캐시에 저장.
    - 다음 빌드(요구사항 변경이 없거나 일부 변경): 이미 캐시된 다운로드를 사용 → 네트워크 요청·시간 절감.
- **중요**: 이 캐시 디렉토리는 **최종 이미지에 포함되지 않음**. (캐시는 빌드 환경의 오버레이)
- Terraform/CI 영향: 네트워크 사용량 및 빌드 시간 큰 폭 감소 → 자주 배포되는 인프라에서 비용 절감.

실제 빌드 시간 차이 (캐시 지우고 진행: docker builder prune -a)
- 개선 전: 빌드 - 24.8s / 재빌드 - 0.8s
- 개선 후: 빌드 - 24.9s / 재빌드 - 0.8s


#### 2-3. ECR push

$ECR_URI 조회 명령어

```
terraform -chdir=../terraform output -raw ecr_repository_url
```

로그인

```
# 형식
aws ecr get-login-password --region $REGION \
  | docker login --username AWS --password-stdin $ECR_URI
```

```
# 예시
aws ecr get-login-password --region ap-northeast-2 \
  | docker login --username AWS --password-stdin 716174522908.dkr.ecr.ap-northeast-2.amazonaws.com
```

Dockerfile 이미지 빌드

```
docker build -t url-shortener .
```

ECR push

```
docker push $ECR_URI:$IMAGE_TAG
```

> [!tip] 지역 변수를 설정하고 명령어를 실행하면 더 편함
> ```bash
> REGION=ap-northeast-2
> ECR_URI=$(terraform -chdir=../terraform output -raw ecr_repository_url)
> GIT_SHA=$(git rev-parse --short HEAD)
> IMAGE_TAG="sha-${GIT_SHA}"
> ```
>
> Terraform output으로 ECR URL을 가져오고, Git SHA를 이미지 태그로 사용하는 패턴
> 
> ```
> aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin $ECR_URI
> 
> docker build -t $ECR_URI:$IMAGE_TAG .
> 
> docker push $ECR_URI:$IMAGE_TAG
> ```

values.prod.yaml 수정

```
api:
  image:
    repository: <ECR_URI>     
    tag: sha-abc1234          # 위에서 push한 IMAGE_TAG 값으로 설정
    pullPolicy: IfNotPresent  # Never → IfNotPresent 변경 필수
    
postgres:
  storageClass: gp3  # standard → gp3 변경 (EKS 권장, 더 빠르고 저렴)
```

### 3. ArgoCD HA 설치 (고가용성 구성 목적)

고민한 부분

**단일 Pod ArgoCD의 문제점**
: replicas=1 (기본값). 단일 Pod가 죽으면 GitOps 동기화가 멈추게됨
 운영환경에서 ArgoCD가 다운되면 아래와 같은 문제가 발생함.
 
 1. Git 변경이 클러스터에 반영되지 않음
 2. 개발팀은 배포가 안된다는 사실을 모를 수 있음
 3. 긴급 배포(Hotfix) 시 ArgoCD를 먼저 복구해야 하는 상황이 생김

> default로 server.replicas=2, applicationController.replicas=2로 HA 구성을 한다고 함

**argocd-values.yaml로 설치하는 이유**
- --set 옵션으로 설치하면 설정이 코드로 남지 않음
- 파일로 관리하면 팀원이 동일한 환경으로 설치가 가능하고, Git에 커밋되어 ArgoCD 설정 자체가 GitOps로 관리됨. 무엇보다 변경 내용 추적이 용이함

>단, 이건 나중에. 일단 Helm 으로 설치

#### kubectl로 로컬에서 EKS 클러스터에 접근할 수 있게 설정

```
aws eks update-kubeconfig --region ap-northeast-2 --name url-shortener
```

#### argocd namespace 생성

kubernetes는 namespace를 사용해 논리적으로 공간을 격리하여 리소스들은 관리할 수 있다는 점을 잊지말자.

```
kubectl create namespace argocd
```

- 확인 명령어

```
kubectl get namespace argocd
```

#### Helm으로 ArgoCD 설치

```
helm repo add argo https://argoproj.github.io/argo-helm
helm repo update
```

```
helm install argocd argo/argo-cd \
  --namespace argocd \
  --version 7.3.4 \
  --set server.service.type=ClusterIP \
  --set configs.params."server\.insecure"=true
```

**고민 부분: ClusterIp vs LoadBalancer**

LB를 사용하면 외부에서 직접 ArgoCD UI에 접근할 수 있음. 하지만 ALB 생성에 시간이 걸릴 뿐더러 현재 단계에서는 ingress가 비활성화 되어 있어 HTTPS 지원도 안됨.
그래서, ClusterIP를 사용해 기본적으로 외부 접근을 차단했고, 외부 접근시 port-forwarding을 사용해서 접근 가능함.

### ArgoCD UI 접속

- ArgoCD 초기 admin 비밀번호 조회 (처음 설치하면 자동으로 설정되는 기본 pw가 있음)

```
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d && echo
```
username: admin (기본)

- 로그인: 기본은 8080:443 터널링이지만 https 지원이 현재 설정상 안되어 80으로 재설정
```
kubectl port-forward svc/argocd-server -n argocd 8080:80
```


```
argocd login localhost:8080 --username admin --password <초기비밀번호> --insecure
```
