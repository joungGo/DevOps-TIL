### EKS 아키텍처 — 트래픽 흐름 시나리오

```md
VPC (네트워크 공간)
├── Subnet (층/구역)
│   ├── EC2 Instance = EKS Worker Node  ← 이게 실제 인스턴스
│   │   └── Pod (컨테이너)              ← 인스턴스 위에서 실행
│   └── NAT Gateway                    ← AWS 관리형 서비스 (인스턴스 아님)
└── Internet Gateway                   ← AWS 관리형 서비스 (인스턴스 아님)
```

#### 1. Pod에서 외부 인터넷(curl)으로 나가는 흐름(아웃바운드)

Pod가 외부로 패킷을 생성하면 Pod IP는 veth pair를 통해 Node 네트워크로 전달되며, 환경에 따라 Node의 iptables에서 Pod IP가 Node IP로 SNAT될 수 있습니다. 이후 패킷은 프라이빗 서브넷의 라우트 테이블을 따라 NAT Gateway로 전달되고, NAT Gateway에서 내부 IP(Node IP 또는 Pod IP)가 EIP(공인 IP)로 SNAT된 뒤 IGW를 통해 인터넷으로 나가게 됩니다. 이 과정에서 외부 인터넷에서는 NAT Gateway에 연결된 EIP만 보이고 내부 사설 IP는 노출되지 않습니다. 다만 AWS VPC CNI 환경에서는 Pod가 VPC IP를 직접 사용하므로 Node 단계의 SNAT이 생략되는 경우가 일반적이며, 이 경우 NAT Gateway에서 한 번만 SNAT이 수행됩니다.

응답의 경우, Google → EIP → NAT GW (Connection Table 역조회) → Node → iptables DNAT → Pod. 비동기 UDP라면 연결 추적이 없어 응답이 드롭될 수 있음 (stateful 방화벽 개념).

> - EIP는 인스턴스 ip가 아니라 외부 공인 ip를 의미함.
> - AWS VPC CNI를 사용하는 경우 pod ip를 노드(인스턴스 ip)로 변환하는 과정이 생략됨

> [!info] Pod / Node / ENI & 네트워크 개념 정리
> **Pod / Node / ENI**
> - **Pod**: 컨테이너가 실행되는 논리 단위. Pod에는 사설 IP(예: 10.0.10.5)가 있음.
> - **Node**: Pod가 실제로 동작하는 VM(또는 인스턴스). Node는 자체 IP(예: 10.0.10.x)를 가짐.
> - **ENI (Elastic Network Interface)**: AWS에서 VM/리소스에 붙이는 네트워크 인터페이스. 일부 CNI(예: AWS VPC CNI)는 Pod에 직접 ENI를 붙이기도 함(→ SNAT 불필요할 수 있음).
>
> **veth pair (가상 이더넷 쌍)**
> - Pod 네트워크와 Node 네트워크를 연결하는 가상의 케이블
> - 한쪽은 Pod 네임스페이스, 다른 쪽은 Node 네임스페이스에 연결
>
> **iptables (kube-proxy)**
> - Node에서 패킷을 변형하거나 포워딩하는 리눅스 커널 수준 트래픽 처리 도구
> - POSTROUTING 체인에서 SNAT 적용되는 경우 많음
>
> **SNAT / DNAT / Connection tracking**
> - **SNAT**: 내부 IP → 공인 IP 변환 (예: 10.0.10.5 → EIP)
> - **DNAT**: 응답 패킷 목적지 IP를 내부 IP로 변환
> - **Connection tracking**: NAT 장비가 연결 상태 저장 후 응답을 올바른 내부 IP/포트로 전달
>
> **Route table (라우팅 테이블)**
> - 서브넷 트래픽 경로 규칙
> - 예: 0.0.0.0/0 → NAT Gateway (프라이빗 서브넷 인터넷 접근)
>
> **NAT Gateway vs IGW**
> - **IGW (Internet Gateway)**: 퍼블릭 IP가 붙은 리소스가 인터넷과 직접 통신하도록 지원
> - **NAT Gateway**: 프라이빗 리소스가 인터넷으로 나갈 때 여러 내부 IP를 공인 IP(EIP)로 SNAT
> - 응답은 NAT Gateway의 연결 테이블 기반으로 역방향 전달

> [!info] AWS VPC CNI를 사용하는 이유와 상황
> 
> ---
> 
> #### 핵심 이유 — Pod가 VPC IP를 직접 가짐
> 
> 일반 CNI는 Pod에 가상 IP(192.168.x.x)를 부여합니다. VPC가 이 IP를 모르기 때문에 캡슐화가 필요합니다.
> 
> VPC CNI는 Pod에 **실제 VPC IP(10.0.x.x)**를 직접 부여합니다. VPC가 Pod를 EC2처럼 인식합니다.
> 
> ```
> 일반 CNI:
> Pod IP = 192.168.1.2 (VPC가 모르는 IP)
> → Node IP로 SNAT 필수
> → NAT GW에서 또 SNAT
> → SNAT 2번 발생
> 
> AWS VPC CNI:
> Pod IP = 10.0.10.11 (VPC가 아는 IP)
> → Node SNAT 생략
> → NAT GW에서만 SNAT
> → SNAT 1번만 발생
> ```

> [!tip] 기술적으로 어떻게 Pod에 VPC IP를 주나
> 
> ENI(Elastic Network Interface)를 Node에 추가로 붙이고, 그 ENI의 Secondary IP를 Pod에 할당합니다.
> 
> ```
> Node (t3.medium)
> ├── eth0 (Primary ENI)
> │     Primary IP: 10.0.10.5  ← Node 자신의 IP
> │     Secondary IP: 10.0.10.11 → Pod-A에 할당
> │     Secondary IP: 10.0.10.12 → Pod-B에 할당
> │
> └── eth1 (Secondary ENI)
>       Secondary IP: 10.0.10.21 → Pod-C에 할당
>       Secondary IP: 10.0.10.22 → Pod-D에 할당
> ```
> 
> Pod는 veth pair로 이 Secondary IP와 연결됩니다.

> [!important] 사용하는 이유 4가지
> 
> **① SNAT 단계 감소 → 원본 IP 보존**
> 
> ```
> VPC CNI 없을 때:
> 외부 서비스 로그 → Node IP만 보임
> Pod가 어디서 요청했는지 추적 불가
> 
> VPC CNI 있을 때:
> NAT GW 안쪽에서는 Pod IP 그대로 보임
> → 어느 Pod에서 요청했는지 추적 가능
> → 디버깅, 보안 감사에 유리
> ```
> 
> **② 성능 — 캡슐화 오버헤드 없음**
> 
> ```
> Flannel/Calico (오버레이):
> Pod 패킷 → VXLAN 캡슐화 → 전송 → 역캡슐화
> → CPU 사용 증가, 지연시간 증가
> 
> VPC CNI:
> Pod 패킷 → 그대로 전송
> → 오버헤드 없음
> → 고성능 네트워크 처리 필요한 앱에 유리
> ``` 
>
> 
> **③ Security Group을 Pod 단위로 적용 가능**
> 
> **네트워크 권한을 서비스 단위로 분리할 수 있기 때문**입니다.
> 
> ```
> 일반 CNI:
> Security Group → Node(EC2) 단위만 적용
> 같은 Node의 모든 Pod가 동일한 SG 공유
> 
> VPC CNI:
> Security Group for Pods 기능 사용 시
> Pod마다 개별 SG 적용 가능
> 
> 예시:
>   DB Pod    → DB SG (3306 포트만 허용)
>   API Pod   → API SG (8080 포트만 허용)
>   Admin Pod → Admin SG (추가 포트 허용)
> ```
> 
> >SG는 ENI를 기준으로 적용할 수 있음. 일반 CNI의 경우 노드에만 ENI가 붙어 있어 pod별 SG 관리가 안되지만, VPC CNI 환경의 경우 pod가 ENI/IP를 직접 이용할 수 있으므로 SG를 Pod별로 관리할 수 있게 됨.
> 
> **④ AWS 서비스와 네이티브 연동**
> 
> ```
> EKS가 기본으로 VPC CNI를 설치함
> → ALB, NLB가 Pod IP를 직접 타겟으로 등록 가능
>    (target-type: ip 모드)
> → VPC Flow Logs에서 Pod IP 단위 트래픽 확인
> → AWS PrivateLink와 직접 연동
> ```

> [!example] 사용하는 상황
> 
> ```
> ✓ EKS를 쓰는 모든 경우 (기본값이므로)
> ✓ Pod 단위 보안 제어가 필요할 때
> ✓ 낮은 레이턴시가 중요한 서비스 (금융, 게임)
> ✓ ALB target-type=ip 모드를 쓸 때
> ✓ VPC Flow Logs로 Pod 트래픽을 추적해야 할 때
> ✓ 크로스 AZ Pod 통신이 잦을 때
> ```

> [!warning] 단점 — 언제 다른 CNI를 고려하나
> 
> VPC CNI의 유일한 단점은 **Pod 수 제한**입니다.
> 
> ```
> t3.medium 기준:
>   ENI 최대 3개 × ENI당 IP 6개 - 1 (Node 자신) = 17개 Pod
> 
> Pod를 많이 띄워야 하는 경우:
>   → 인스턴스 타입을 올리거나
>   → VPC CNI의 prefix delegation 기능 사용
>      (ENI당 /28 블록 할당 → Pod 수 대폭 증가)
>   → 또는 Cilium 같은 다른 CNI 고려
> ```

> [!summary] 한 줄 요약
> 
> ```
> AWS VPC CNI = Pod에 실제 VPC IP를 줘서
> 캡슐화 제거 + 성능 향상 + Pod 단위 보안 제어를
> 가능하게 하는 EKS 기본 네트워크 플러그인
> ```


#### 2. 외부 -> pod (인바운드)

외부 클라이언트가 ALB DNS로 요청하면 ALB를 통해 Kubernetes Node와 Pod로 전달됩니다. 기본 설정에서는 중간 SNAT으로 인해 Pod에서 클라이언트 IP가 보존되지 않지만, Service에 externalTrafficPolicy=Local을 설정하면 Node 단계의 SNAT을 방지하여 원본 IP를 유지할 수 있습니다. 또한 ALB는 X-Forwarded-For 헤더에 클라이언트 IP를 포함하므로 Pod에서는 해당 헤더를 통해 원본 IP를 확인할 수 있으며, 실무에서는 externalTrafficPolicy=Local과 ALB 헤더를 함께 사용하는 방식이 일반적입니다.

> [!info] externalTrafficPolicy=Local 과 X-Forwarded-For 를 함께 사용하는 이유
> 
> `externalTrafficPolicy=Local` 과 ALB의 `X-Forwarded-For` 헤더는 **서로 보완적인 정보**를 제공하기 때문에 같이 사용하는 것이 일반적입니다.
> 
> #### 1️⃣ externalTrafficPolicy=Local 만 사용할 때의 한계
> 
> - Pod에서 **source IP는 보존됨**
>     
> - 하지만 **프록시 체인 정보는 알 수 없음**
>     
> 
> ```
> Client → CloudFront → ALB → Pod
> ```
> 
> Pod에서 보이는 값
> 
> ```
> src_ip = ALB IP (또는 마지막 프록시 IP)
> ```
> 
> → 실제 클라이언트가 아니라 **중간 프록시만 보일 수 있음**
> 
> ---
> 
> #### 2️⃣ X-Forwarded-For 만 사용할 때의 한계
> 
> - 헤더는 **변조 가능**
>     
> - 네트워크 레벨에서 신뢰할 수 없음
>     
> 
> ```
> curl -H "X-Forwarded-For: 8.8.8.8"
> ```
> 
> → 애플리케이션이 그대로 믿으면 위험
> 
> ---
> 
> #### 3️⃣ 둘을 같이 사용하면
> 
> 네트워크 레벨 + 애플리케이션 레벨 검증 가능
> 
> ```
> src_ip = 1.2.3.4
> X-Forwarded-For = 1.2.3.4, 10.0.1.23
> ```
> 
> - `src_ip` → 신뢰 가능한 실제 접속 IP
>     
> - `X-Forwarded-For` → 프록시 체인 전체 정보
>     
> 
> → 서로 cross-check 가능
> 
> ---
> 
> #### 4️⃣ 실무에서 중요한 이유
> 
> **① 보안**
> 
> - IP 기반 차단
>     
> - 헤더 변조 탐지 가능
>     
> 
> **② 로깅**
> 
> - 실제 사용자 IP 기록
>     
> - CDN / ALB 경유 정보 기록
>     
> 
> **③ 프록시 환경 대응**
> 
> - CloudFront + ALB 같이 쓰는 경우 필수
>     
> 
> ---
> 
> #### 한 줄 정리
> 
> ```
> externalTrafficPolicy=Local = 신뢰 가능한 실제 IP
> X-Forwarded-For = 프록시 경유 정보
> → 둘을 같이 사용해야 정확하고 안전
> ```

> [!warning] 클라이언트 IP 유실 핵심 정리
> **흐름**
> ```
> Client(1.2.3.4)
>    ↓
> ALB
>    ↓ SNAT
> Node(10.0.x.x)
>    ↓
> Pod
> ```
>
> **왜 유실되나?**
> - 중간 네트워크 장비가 **SNAT(출발지 IP 변경)** 수행
> - Pod가 보는 source IP = **실제 클라이언트 ❌ / 중간 장비 IP ⭕**
> - 발생 지점: ALB, Kubernetes Node(iptables masquerade), NAT Gateway
>
> **왜 문제인가?**
> - **보안**: IP 기반 차단/공격 탐지 불가
> - **로그 추적**: 사용자 식별 불가
> - **위치 기반 처리**: GeoIP/CDN 최적화 불가
> - **Rate limiting**: 모든 요청이 동일 IP → 정상 사용자까지 차단
>
> **한 줄 정리**
> - SNAT으로 원본 클라이언트 IP가 유실되면 보안·로그·위치 기반 처리·rate limiting이 불가능하므로 원본 IP 보존이 중요함
#### 3. pod <-> pod 간 통신

Pod 간 통신 시 먼저 CoreDNS가 Service 이름을 ClusterIP(목적지)로 변환하고, kube-proxy의 iptables가 ClusterIP를 실제 Pod IP로 DNAT하여 트래픽을 전달한다. AWS VPC CNI 환경에서는 Pod가 실제 VPC IP를 사용하므로 오버레이 없이 VPC 라우팅으로 크로스 노드 통신이 가능하며, Service를 사용해야 안정적인 가상 IP, 로드밸런싱, readiness 기반 endpoint 관리가 가능하다.

![[pod_to_pod_via_service_flow 1.html]]
##### 1️⃣ DNS 조회 (Service 이름 → ClusterIP)

Pod-A가  
`http://my-svc.default.svc.cluster.local` 호출하면

→ CoreDNS 가 Service 이름을  
→ **ClusterIP (가상 IP)** 로 변환합니다.

즉:

```
my-svc.default.svc.cluster.local
        ↓
10.96.0.1 (ClusterIP)
```

---

##### 2️⃣ iptables DNAT (ClusterIP → Pod IP)

ClusterIP는 실제 존재하는 IP가 아니라 **가상 IP**입니다.

그래서 kube-proxy의 iptables가:

```
dst = ClusterIP
```

를 발견하면

→ 실제 Endpoint 중 하나로 **DNAT** 합니다.

```
10.96.0.1  →  10.0.11.8 (Pod-B)
```

여기서 **로드밸런싱도 같이 수행**됩니다.

---

##### 3️⃣ 크로스 노드 통신 (AWS VPC CNI)

이 그림의 핵심 포인트 👍

AWS VPC CNI 를 쓰면

- Pod가 **VPC 실제 IP**를 가짐
    
- 오버레이 네트워크 없음
    
- VXLAN 없음
    
- 바로 VPC 라우팅으로 통신
    

즉:

```
Pod-A (AZ-a)
   ↓
VPC routing
   ↓
Pod-B (AZ-c)
```

추가 캡슐화 없음 → 성능 좋음 🚀

---

##### 4️⃣ NetworkPolicy 적용 지점

NetworkPolicy는:

- Pod ingress/egress 기준
    
- iptables 또는 eBPF로 적용
    

>**한 줄 정리:**  
NetworkPolicy는 Kubernetes 에서 Service를 통해 DNAT되어 Pod 간 통신이 자유롭게 이루어지는 과정에서 불필요한 접근까지 허용되는 것을 막기 위해, label 기반으로 Pod 간 ingress/egress 트래픽을 제어하는 네트워크 방화벽 규칙이다. 🔐

실무 패턴:

```
default deny
+
필요한 것만 allow
```

---

kube-proxy의 DNAT 과정은 CNI와 무관하게 동작하며 Service IP를 Pod IP로 변환하는 역할만 수행한다. AWS VPC CNI를 사용하는 경우 Pod가 실제 VPC IP를 할당받기 때문에 VXLAN 같은 오버레이 네트워크가 필요 없고, AWS VPC의 기본 라우팅을 통해 크로스 노드 Pod 간 직접 통신이 가능하다.

#### 4. Lens 툴에서 어떻게 AWS의 리소스들이 조회될까?

EKS에서 `kubectl` 또는 Lens로 클러스터에 접근할 때는 kubeconfig의 `exec` 설정에 따라 `aws eks get-token` 명령이 실행됩니다. 이 명령은 AWS STS에서 IAM 기반 임시 토큰을 발급받고, 해당 토큰을 `Authorization: Bearer` 헤더에 담아 EKS API Server로 요청을 보냅니다. 이후 API Server는 토큰을 검증하고, `aws-auth ConfigMap`과 RBAC 규칙을 통해 권한을 확인한 뒤 리소스 조회를 허용합니다.

+ 테라폼에서 `endpoint_public_access = true` 옵션이 true로 되어 있어야 함.
