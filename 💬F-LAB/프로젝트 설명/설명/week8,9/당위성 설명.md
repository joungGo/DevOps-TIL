## Postgresql을 RDS로 변경하는 이유

---

**1. 운영 부담 제거**

PostgreSQL을 직접 K8s StatefulSet으로 운영하면 백업, 패치, 장애 복구를 직접 해야 해요. RDS는 AWS가 자동으로 처리해줘서 개발팀이 DB 운영 대신 서비스 개발에 집중할 수 있어요.

---

**2. 데이터 영속성 보장**

K8s Pod은 재시작되면 데이터가 날아갈 수 있어요. PVC를 붙여도 노드 장애 시 위험해요. RDS는 EBS 기반으로 데이터가 Pod 생명주기와 완전히 분리돼 있어요.

---

**3. 읽기 트래픽 분산 (Read Replica)**

트래픽이 늘어날수록 DB가 병목이 돼요. RDS Read Replica를 붙여서 쓰기는 Primary, 읽기는 Replica로 분리하면 Primary 부하를 줄이고 수평 확장이 가능해요. K8s PostgreSQL로 동일한 구성을 만들려면 복잡한 설정이 필요해요.

> [!info] db connection pool size 관리
> #### db connection pool size 관리
>
> **Connection Pool 관리 측면에서의 RDS 전환 이유**
>
> K8s PostgreSQL은 `max_connections`를 직접 설정하고 관리해야 해요. 설정이 잘못되면 연결 초과로 `too many connections` 에러가 발생하고 서비스 장애로 이어져요.
>
> RDS는 인스턴스 타입(메모리)에 따라 `max_connections`가 자동으로 결정돼요.
>
> ```
> db.t3.micro max_connections = DBInstanceClassMemory / 9531392
> 1,073,741,824 bytes / 9,531,392 ≈ 85개
> ```
>
> 이 공식을 기반으로 Connection Pool을 설계할 수 있어요.
>
> ```
> Pod 2개 × (pool_size=5 + max_overflow=10) = 최대 30 연결
> → max_connections 85개 중 35% 사용 → 안정적 운영 가능
> ```
>
> 인스턴스를 스케일업(`db.t3.micro` → `db.t3.medium`)하면 메모리가 늘어나고 `max_connections`도 자동으로 늘어나요. K8s PostgreSQL처럼 설정 파일을 수동으로 변경하고 재시작할 필요가 없어요.
