### 내가 알고 있던 내용

EKS 리소스는 기본적으로 aws 리소스에 접근하지 못해. 그래서 필요한게 IRSA야. IAM Role ServiceAccount의 약자로, pod가 aws 리소스에 접근할 수 있는 권한을 획득하는 방법을 말해. pod가 정의된 serviceAccount를 사용해 IAM Role에 연결해 aws 리소스에 접근하는 구조야. serviceaccount는 aws에 접근할 때 사용하는 계정이고, IAM Role은 권한이라고 생각하면 돼. serviceaccount 계정을 어떤 권한을 사용할 수 있는지 역할인 IAM Role에 연결하여 해당 권한 범위에서 aws 리소스에 접근해 작업을 할 수 있어.

### 수정 (Summary)

ServiceAccount는 Kubernetes에서 Pod의 신원(identity)을 나타내는 객체.
IAM Role은 권한 정책을 가진 AWS IAM 엔티티.
> IRSA는 EKS에서 Kubernetes ServiceAccount와 AWS IAM Role을 연결하여 Pod 단위로 AWS 권한을 안전하게 부여하는 방식이다.

---
### 전체

EKS의 Pod는 기본적으로 AWS API를 호출할 수 있는 IAM 권한이 없다.  
그래서 Pod가 S3, DynamoDB, SQS 같은 AWS 리소스에 접근하려면 IAM 권한을 부여해야 하는데, 이를 위한 대표적인 방식이 IRSA(IAM Roles for Service Accounts)다.

IRSA는 Kubernetes의 ServiceAccount와 AWS IAM Role을 연결하는 방식이다.

Pod는 특정 ServiceAccount를 사용하도록 설정되고,  
그 ServiceAccount에 연결된 IAM Role을 Assume 하여 AWS 리소스에 접근한다.

여기서:

- ServiceAccount  
    → Kubernetes 내부에서 Pod의 실행 주체(identity)를 나타냄
    
- IAM Role  
    → AWS 리소스 접근 권한 정책을 담고 있음
    

즉,  
“어떤 Pod가 어떤 AWS 권한을 사용할 수 있는지”를  
ServiceAccount와 IAM Role 매핑으로 제어하는 구조다.

동작 흐름은 대략 아래와 같다.

1. Pod가 특정 ServiceAccount 사용
    
2. 해당 ServiceAccount에 IAM Role ARN annotation 존재
    
3. EKS의 OIDC Provider를 통해 신뢰 검증
    
4. Pod가 STS AssumeRoleWithWebIdentity 호출
    
5. 임시 AWS Credential 발급
    
6. 해당 권한 범위 내에서 AWS 리소스 접근

특히 수정하면 좋은 부분:

> serviceaccount는 aws에 접근할 때 사용하는 계정

이 표현보다는:

> ServiceAccount는 Kubernetes에서 Pod의 신원(identity)을 나타내는 객체

라고 하는 게 더 정확해.

또:

> IAM Role은 권한

도 완전히 틀린 건 아니지만:

> IAM Role은 권한 정책을 가진 AWS IAM 엔티티

정도로 표현하면 면접에서도 더 좋다.

면접용으로 한 줄로 압축하면:

> IRSA는 EKS에서 Kubernetes ServiceAccount와 AWS IAM Role을 연결하여 Pod 단위로 AWS 권한을 안전하게 부여하는 방식이다.
