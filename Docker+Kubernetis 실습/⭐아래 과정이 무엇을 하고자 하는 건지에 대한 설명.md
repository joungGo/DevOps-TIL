# 1️⃣ 전체 개요 — 이 실습의 진짜 목적은 무엇인가?

[[Docker → Kubernetes Cluster → Service → Pod의 의미와 각 필요성 및 네트워크 구조 흐름]]

이 문서가 최종적으로 하고자 하는 일은 한 문장으로 말하면 이거야.

> **“로컬 PC에서 Kubernetes 클러스터를 직접 구성하고,  
> Docker → Pod → Service(NodePort)까지  
> 컨테이너 서비스가 외부에서 어떻게 접근되는지 전체 흐름을 이해한다.”**

조금 더 풀면, 목표는 크게 4단계야.

---

## 🎯 최종 목표를 단계로 나누면

### ① 가짜 서버가 아니라 **진짜 서버처럼 동작하는 VM 환경** 만들기

- Vagrant + VirtualBox로
    
- Master 1대, Worker 2대
    
- 실제 서버처럼 **고정 IP, 네트워크 분리(NAT / Host-only)**
    

👉 “내 노트북 안에 데이터센터 하나 만든다”에 가까움

---

### ② Kubernetes가 싫어하는 환경 요소를 전부 제거

- swap 비활성화
    
- 커널 네트워크 옵션 설정
    
- hostname / hosts 정확히 맞춤
    

👉 “쿠버네티스가 정상 동작할 수 있는 **운영체제 레벨 환경** 만들기”

---

### ③ Docker → Kubernetes로 자연스럽게 넘어가기

- 먼저 Docker 단독으로 nginx 실행
    
- 포트 바인딩 직접 체험 (`-p 80:80`)
    
- 그 다음 Kubernetes에서 같은 nginx를 Pod + Service로 실행
    

👉 “Docker 포트 바인딩 vs Kubernetes Service 차이 체감”

---

### ④ 최종적으로 이해하려는 핵심 질문

이 실습을 끝내면 이 질문들에 답할 수 있어야 해.

- Pod는 왜 직접 접속이 안 될까?
    
- Service(NodePort)는 왜 모든 노드에서 접속이 될까?
    
- Docker `-p`랑 Kubernetes Service는 뭐가 다를까?
    
- 클러스터 네트워크는 어디서 시작해서 어디서 끝날까?

# 2️⃣ 큰 흐름으로 본 전체 단계 지도

```text
[Host PC]
   ↓ (Vagrant)
[VM 3대 생성]
   ↓
[OS / 커널 / 네트워크 준비]
   ↓
[Docker 설치]
   ↓
[Docker로 nginx 실행]
   ↓
[Kubernetes 설치]
   ↓
[클러스터 구성 (Master / Worker)]
   ↓
[Pod 생성]
   ↓
[Service(NodePort)로 외부 노출]
```

이제 이 흐름 안에서 **각 단계와 명령어가 어떤 역할을 하는지** 설명할게.

---

# 3️⃣ 단계별 목적 + 명령어 의미 설명

## 0️⃣ 실습 환경 전제

### 왜 이 단계가 필요한가?

- Kubernetes는 **단일 서버 실습**보다
    
- **멀티 노드 환경**에서 개념이 훨씬 잘 보임
    
- 실제 회사 환경과 구조가 거의 같음
    

### Vagrant + VirtualBox의 역할

- Vagrant: VM 생성 자동화 도구 (서버 장비 관리자)
    
- VirtualBox: 실제 가상 머신 실행 엔진
    

👉 “VM을 수동 설치하지 않고 코드로 관리”

---

## 1️⃣ Vagrant 기반 VM 생성 및 접속

### `vagrant up`

**역할**

- Vagrantfile을 읽어서
    
    - VM 생성
        
    - 네트워크 설정
        
    - 포트 포워딩 설정
        
- 사람이 설치 화면을 클릭할 필요 없음
    

👉 “서버 3대를 동시에 자동 설치”

---

### `vagrant ssh`

**역할**

- SSH 키, 계정, 포트 전부 자동 처리
    
- 사용자는 그냥 접속만 하면 됨
    

👉 “접속 자체는 중요하지 않음 → **관리 자동화 경험**이 핵심”

---

## 2️⃣ 사전 준비 (Kubernetes가 싫어하는 것 제거)

이 단계는 전부 **“왜 Kubernetes는 이걸 요구할까?”**를 생각하면 이해가 쉬워.

---

### 2-1. root 계정 전환

**이유**

- 네트워크, 커널, 시스템 설정은 일반 유저 불가
    
- 실습에서는 편의상 root 사용
    

👉 운영환경에서는 sudo 권장

---

### 2-2. SWAP 비활성화

```bash
swapoff -a
```

**왜 Kubernetes는 swap을 싫어할까?**

- Kubernetes는 **리소스 계산을 매우 엄격하게** 함
    
- swap이 있으면
    
    - 실제 메모리 사용량 추적 불가능
        
    - Pod eviction 판단이 틀어짐
        

👉 “클러스터 안정성 때문에 강제 금지”

---

### 2-3. 브리지 네트워크 커널 옵션

이 부분은 **쿠버네티스 네트워크의 핵심 준비 작업**이야.

**무슨 문제를 해결하나?**

- Pod ↔ Pod 트래픽은 브리지 네트워크를 통과
    
- 기본 Linux는 이 트래픽을 iptables로 안 봄
    

**그래서**

- `br_netfilter` 로드
    
- bridge 트래픽도 iptables 규칙 적용
    

👉 “Pod 네트워크를 OS 방화벽/정책과 연결”

---

### 2-4. Hostname / hosts 설정

**왜 중요한가?**

- Kubernetes는
    
    - 노드를 이름으로 식별
        
    - 인증서에도 hostname 사용
        

**설정 안 하면**

- `kubeadm join` 실패
    
- 인증서 오류
    
- 노드 NotReady
    

👉 “IP만 맞아도 되는 게 아님”

---

## 3️⃣ Docker 설치

### 이 단계의 진짜 목적

> “Kubernetes가 컨테이너를 실행할 **엔진** 준비”

Docker는 지금 당장은 nginx를 띄우는 용도지만,  
곧 **kubelet이 컨테이너를 실행할 런타임**이 됨.

---

### Docker 단독 nginx 실행의 의미

```bash
docker run -p 80:80 nginx
```

이건 단순 테스트가 아니라 **비교 기준**이야.

- Docker:
    
    - 호스트 포트 ↔ 컨테이너 포트 직접 연결
        
- Kubernetes:
    
    - Pod는 포트 바인딩 없음
        
    - Service가 중간에 개입
        

👉 나중에 Service 개념 이해를 위해 일부러 먼저 실행

---

## 4️⃣ Kubernetes 설치

### kubeadm / kubelet / kubectl 역할 분리

- kubeadm: 클러스터 설치 관리자
    
- kubelet: 각 노드의 현장 관리자
    
- kubectl: 사용자 조종기
    

👉 “설치 / 실행 / 제어 역할이 완전히 분리됨”

---

### cgroup driver 통합

**왜 이 설정이 중요할까?**

- Docker와 kubelet의 cgroup 방식이 다르면
    
    - 노드 상태 불안정
        
    - Pod 랜덤 종료
        

👉 “컨테이너 리소스 관리 기준을 하나로 통일”

---

## 5️⃣ Master 초기화

```bash
kubeadm init
```

이 명령 하나로 실제로는 이걸 함:

- etcd 생성
    
- API Server 실행
    
- Scheduler 실행
    
- Controller Manager 실행
    
- 인증서 생성
    

👉 “클러스터의 심장 생성”

---

## 6️⃣ Worker Join

```bash
kubeadm join
```

**이건 단순 접속이 아님**

- Master의 CA 인증서 신뢰
    
- 노드 인증
    
- 클러스터 구성원 등록
    

👉 “서버가 조직에 입사하는 절차”

---

## 7️⃣ Pod + Service 테스트

### Pod

- 컨테이너 실행 단위
    
- IP는 있지만 **외부 접근 불가**
    

### Service(NodePort)

- Pod 앞에 있는 네트워크 창구
    
- 모든 노드에 포트 개방
    

👉 여기서 핵심 깨달음:

> **“Kubernetes에서는 컨테이너를 직접 노출하지 않는다.”**

---

# 4️⃣ 최종적으로 이 실습이 만들어낸 것

이 실습이 끝나면 네 환경에는:

- 실제 서버 구조와 동일한 클러스터
    
- Docker / Kubernetes 네트워크 차이 이해
    
- Ingress, LoadBalancer로 확장 가능한 기반
    

이 상태에서 다음으로 넘어가면 자연스럽게 이어져:

- Deployment
    
- ReplicaSet
    
- Service 종류 비교
    
- Ingress Controller
