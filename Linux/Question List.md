### 1장
- 커널이 필요한 이유?
    - 프로세스 간 명령어 처리에 있어서 같은 공간에 대해 복수의 명령어 처리로 인해 데이터 손실 발생 가능. 이는 **복수의 프로세스가 동시에 저장 장치에 접근이 가능하기 때문**
    - 커널의 커널 모드를 사용해 커널을 통해서만 저장 장치에 접근할 수 있도록 제한을 두어 위의 문제를 해결
- 시스템 콜 래퍼 함수의 필요성
	- 각 프로그램은 고급 언어로 작성되며, 시스템 콜을 직접 호출하지 않고 사용자 공간 라이브러리(libc 등)가 제공하는 시스템 콜 래퍼 함수를 호출한다. 이 래퍼 함수 내부에는 커널로 진입하기 위한 어셈블리 코드가 포함되어 있다.
	  
	  만약 이러한 래퍼 함수가 없다면 각 프로그램마다 시스템 콜 호출을 위한 어셈블리 코드를 직접 작성해야 하므로 비효율적이다.
	  
	  시스템 콜의 실제 구현은 커널에 존재하며, 래퍼 함수를 통해 커널 모드로 전환됨으로써 파일, 디바이스, 네트워크 등 보호된 자원에 안전하게 접근할 수 있다.
- 프로세스와 프로그램의 차이는?
	- 프로그램은 디스크에 저장된 실행 파일이고, 프로세스는 해당 프로그램이 메모리에 올라가 실행 중인 인스턴스이다.
- 프로세스와 스레드의 차이점은?
	- 프로세스는 독립된 가상 메모리 공간을 가지며, 스레드는 하나의 가상 메모리 공간을 공유하되 각자 스택만 따로 가진다.
	  
	  프로세스는 code, data, heap, stack을 모두 독립적으로 가지는 실행 단위이고, 스레드는 하나의 프로세스 안에서 code, data, heap을 공유하되 stack만 개별적으로 가지는 실행 흐름이다.
	- 왜 스택은 공유하지 않을까?
		- 스택은 함수 호출 순서와 반환 주소, 지역 변수 등 스레드의 실행 흐름을 담고 있기 때문에 스레드 간에 공유하면 실행이 꼬여 정상 동작이 불가능하다.
- 정적 라이브러리와 동적 라이브러리의 차이는?
	- 제공하는 기능은 동일하지만 프로그램과 결합되는 방식이 다르다. 
	  
	  프로그램은 소스 코드를 컴파일하여 오브젝트 파일을 생성한 뒤, 오브젝트 파일이 사용하는 라이브러리를 링크하여 실행 파일을 만든다.
	  
	  정적 라이브러리는 링크 시 필요한 라이브러리 함수 코드가 실행 파일에 직접 포함된다. 반면 공유 라이브러리는 실행 파일에 라이브러리 자체가 포함되지 않고, 필요한 라이브러리와 심볼에 대한 정보만 기록된다. 실제 라이브러리는 프로그램 실행 시 동적 링커에 의해 메모리에 로드되며, 해당 라이브러리의 함수를 호출하게 된다.
	- 그래서, 동적 링크한 프로그램의 경우 링크한 동적 라이브러리를 삭제할 경우 실행되지 않습니다.
	- 동적 라이브러리를 더 많이 사용하는 이유는?
		- 시스템에서 차지하는 크기를 줄일 수 있다.
			- 동적 라이브러리를 메모리에 로드하기 때문에 시스템에 차지하는 크기가 작다.
		- 라이브러리에 문제가 있을 경우 공유 라이브러리만 수정 버전으로 교체하기만 하면 해당 라이브러리를 사용하는 모든 프로그램에서 문제가 해결됩니다. 프로그램에 수정을 할 필요가 없습니다.
- 최근에는 정적 라이브러리가 많이 사용된다고 하는데 이유는?
	- 대용량 메모리나 저장 장치의 크기에 제한 받지 않는 시대가 와서 파일 크기 문제는 더 이상 문제가 되지 않습니다.
	- 실행 파일하나로 프로그램이 동작한다면 해당 파일만 복사하면 다른 환경에서도 쉽게 사용이 가능합니다.
	- 실행할 때 공유 라이브러리에 링크하지 않아도 되므로 실행 속도가 더 빠릅니다.
	- 공유 라이브러리의 DDL 지옥 문제 해결 가능
		- 공유 라이브러리의 버전업이 된 경우 하위 버전에 대해서도 자동으로 호환이 될 것 같지만 그렇지 않는 경우가 있어 프로그램이 실행되지 않는 경우가 존재합니다.

### 2장, 3장
- CPU는 동시에 하나의 프로세스만 실행할 수 있는데 왜 우리는 여러 프로그램이 동시에 실행되는 것 처럼 느낄까?
	- `컨텍스트 스위칭` + `매우 빠른 전환` 때문이다.
	1. 프로세스 A 실행 (아주 짧게)
	2. 컨텍스트 스위칭
    3. 프로세스 B 실행
    4. 컨텍스트 스위칭
    5. 프로세스 C 실행
    6. 반복…
    이걸 **1초에 수천~수만 번** 반복함.
	👉 인간의 눈에는 **동시에 실행되는 것처럼 보임**
	이걸 **동시성(concurrency)** 이라고 해.
- 백그라운드 프로세스 그룹이 필요한 이유는?
	- 단말 제어권을 유지한 채로 작업을 병렬로 처리하기 위해 필요하다.
- 프로세스와 데몬의 차이점은?
  
	|구분|백그라운드 프로세스|데몬 프로세스|
	|---|---|---|
	|단말과의 관계|단말에 **의존**|단말과 **완전 분리**|
	|부모 프로세스|보통 `bash`|보통 `init(systemd)`|
	|SIGHUP|단말 종료 시 받음|받지 않음|
	|실행 목적|편의적 병렬 실행|지속적인 서비스 제공|
- N개의 프로세스가 존재할 때, 이상적인 분배는 CPU를 1/N로 배분하는 것이다. 그런데 이렇게 정확하게 배분하는 것이 현실적으로 가능할까?
	- 현실에서는 불가능하다. 그래서 vruntime(가상실행시간)을 사용해 이를 근사한다.
	- vrtuntime += 실제 실행 시간 x 가중치(우선순위)
	- 높은 우선순위는 vruntime 증가 속도가 느리다
	- 우선순위가 높은 프로세스는 더 자주 CPU를 받음
	- vruntime 방식에 타임 슬라이스가 없는 것은 아니다. 이상적 배분 방식과 같이 목표 지연 시간과 최소 실행 시간을 통해 실행 시간을 제한하지만 실제로 고정 타임 슬라이스를 사용하지는 않는다. 즉, 개념적으로는 타임 슬라이스가 존재하지만  구현은 vruntime 기반이다.
- 왜 컨텍스트 스위치가 필요할까?
	- 하나의 논리 CPU는 동시에 하나의 실행 흐름만 처리 가능
	- 여러 프로세스를 동시에 실행하는 것처럼 보이게 하기 위해
    - CPU 자원을 공정하게 분배하기 위해
