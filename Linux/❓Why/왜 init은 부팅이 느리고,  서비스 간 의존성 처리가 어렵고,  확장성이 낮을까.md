좋은 질문이다.  
핵심은 **설계 철학 차이** 때문이다.

SysV init은 “단순한 스크립트 실행기”였고,  
systemd는 “의존성 그래프 기반 관리자”다.

왜 init이 느리고, 의존성 처리가 어렵고, 확장성이 낮았는지 구조적으로 설명해보자.

---

# 1. 왜 부팅이 느렸는가

## 1️⃣ 순차 실행 구조

SysV init은 기본적으로:

```text
S01-service
S02-service
S03-service
...
```

처럼 번호 순서대로 스크립트를 실행한다.

즉:

- 앞의 서비스가 끝날 때까지
    
- 다음 서비스는 시작하지 않음
    

병렬 실행 개념이 거의 없다.

### 결과

- 독립적인 서비스도 기다려야 함
    
- I/O 대기 시간 누적
    
- 전체 부팅 시간 증가
    

---

# 2. 왜 서비스 의존성 처리가 어려웠는가

## 1️⃣ 의존성 표현 방식이 간접적

SysV init에서는:

- 단순히 실행 순서 번호로 의존성 표현
    

예:

```text
S10-network
S20-nginx
```

이렇게 되면 nginx가 network 이후에 실행되긴 하지만,

- network가 실제로 “준비 완료”인지 보장하지 않음
    
- 실패 여부 확인도 제한적
    

## 2️⃣ 명시적 그래프 없음

- 서비스 간 관계를 구조적으로 표현하지 않음
    
- 단순 실행 순서에 의존
    

즉:

```text
의존성 = 실행 순서 암묵적 규칙
```

그래서 복잡한 시스템에서는 관리가 매우 어려웠다.

---

# 3. 왜 확장성이 낮았는가

## 1️⃣ 모든 것이 셸 스크립트

서비스는 단순한:

```bash
/etc/init.d/서비스
```

스크립트였다.

문제:

- 표준화 부족
    
- 배포판마다 구현 차이
    
- 상태 관리 어려움
    
- 재시작 정책 없음
    
- 리소스 제어 없음
    

## 2️⃣ 프로세스 추적 기능 부족

- 부모-자식 관계 추적 불안정
    
- 데몬 포크 시 관리 어려움
    
- 죽은 프로세스 감지 한계
    

현대 환경(컨테이너, 동적 서비스)에는 부족했다.

---

# 4. 구조적 차이 비교

## SysV init

```text
선형 실행 모델
스크립트 중심
순차 처리
의존성 암묵적
```

## systemd

```text
의존성 그래프 기반
unit 정의 파일
병렬 실행
명시적 의존성
cgroup 기반 프로세스 관리
```

---

# 5. 본질적 이유

SysV init은:

> “시스템 시작 시 몇 개의 데몬을 실행하면 된다”는 시대의 설계

하지만 현대 시스템은:

- 네트워크 지연
    
- 동적 장치
    
- 수십~수백 서비스
    
- 컨테이너 환경
    

이런 복잡성을 처리하려면  
단순 스크립트 기반 구조로는 한계가 있었다.

---

# 한 줄 정리

SysV init이 느리고 의존성 처리가 어려웠던 이유는 순차적 스크립트 실행 구조로 설계되어 서비스 간 관계를 명시적으로 표현하지 못했고, 병렬 처리와 현대적 프로세스 관리 기능이 부족했기 때문이다.
