## 컨텍스트 스위치란

**컨텍스트 스위치**는  
CPU가 실행 중인 프로세스(또는 스레드)를 중단하고  
다른 프로세스(또는 스레드)의 실행 상태로 전환하는 작업을 의미한다.

여기서 **컨텍스트(context)** 란:

- CPU 레지스터 값
    
- 프로그램 카운터(PC)
    
- 스택 포인터(SP)
    
- CPU 플래그
    
- 메모리 관리 정보(페이지 테이블 등)
    

즉,

> CPU가 “다음에 이어서 실행하기 위해 반드시 기억해야 하는 상태 전체”

---

## 왜 컨텍스트 스위치가 필요한가

- 하나의 논리 CPU는 동시에 하나의 실행 흐름만 처리 가능
    
- 여러 프로세스를 동시에 실행하는 것처럼 보이게 하기 위해
    
- CPU 자원을 공정하게 분배하기 위해
    

이 역할을 수행하는 과정이 바로 컨텍스트 스위치다.

---

## 컨텍스트 스위치가 발생하는 주요 시점

### 1. 타이머 인터럽트

- 타임 슬라이스 소진
    
- 커널이 강제로 CPU 회수
    
- 다른 실행 가능한 프로세스로 전환
    

---

### 2. I/O 요청

- 프로세스가 시스템 콜을 통해 I/O 요청
    
- 블로킹 발생 → 대기 상태로 전환
    
- 다른 프로세스 실행
    

---

### 3. 선점(preemption)

- 더 높은 우선순위 프로세스 등장
    
- vruntime가 더 작은 프로세스가 깨어남
    

---

### 4. 명시적 상태 변경

- `sleep()`, `wait()`
    
- 시그널 처리
    
- `exit()`
    

---

## 컨텍스트 스위치의 실제 과정

1. 현재 실행 중인 프로세스의 컨텍스트 저장
    
2. 해당 프로세스 상태 변경 (Running → Ready / Sleep)
    
3. 다음 실행할 프로세스 선택 (스케줄러)
    
4. 선택된 프로세스의 컨텍스트 복원
    
5. 프로그램 카운터 위치부터 실행 재개
    

---

## 비용(오버헤드)

컨텍스트 스위치는 **공짜가 아니다**.

발생 비용:

- 레지스터 저장/복원
    
- 캐시 무효화(cache pollution)
    
- TLB flush 가능성
    
- 커널 코드 실행 시간
    

즉,

> 컨텍스트 스위치 자체는 아무 작업도 하지 않지만 CPU 시간을 소비한다.

---
## 성능 관점의 핵심 포인트

- 과도한 컨텍스트 스위치는 성능 저하 원인
    
- CPU bound 작업이 많을수록 스위치 비용이 커짐
    
- I/O bound 작업은 스위치 비용을 숨기기 쉬움
    

---

## 한 문장 요약

> 컨텍스트 스위치는 CPU가 실행 주체를 바꾸기 위해 현재 상태를 저장하고 다른 상태를 복원하는 커널 동작이다.

이제 흐름상 다음으로 이어지면 좋다:

- voluntary / involuntary context switch
    
- `vmstat`, `pidstat`로 측정
    
- 컨텍스트 스위치 최적화 전략
