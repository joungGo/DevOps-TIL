## 1단계: 프로세스의 탄생과 메모리 관리

### 프로세스 생성과 Copy-On-Write (COW)

프로세스가 `fork()`를 호출하면 흥미로운 일이 벌어집니다:

**전통적인 방식이라면:**

- 부모 프로세스의 모든 메모리(코드, 데이터, 힙, 스택)를 물리적으로 복사
- 만약 100MB를 사용 중이라면 100MB를 통째로 복사
- 시간도 오래 걸리고, 메모리도 2배로 소비

**COW의 똑똑한 방식:**

1. **페이지 테이블만 복사**: 부모와 자식 모두 같은 물리 페이지를 가리킵니다
2. **읽기 전용으로 표시**: 양쪽 페이지 테이블 엔트리를 모두 "읽기 전용"으로 설정
3. **쓰기 시도 시 페이지 폴트 발생**:
    - CPU의 MMU가 쓰기 권한 위반을 감지
    - 트랩이 발생하여 커널의 페이지 폴트 핸들러 호출
    - 커널이 실제로는 쓰기 가능한 페이지임을 확인 (COW 플래그 체크)
4. **지연된 복사 실행**:
    - 해당 물리 페이지를 새로 할당
    - 원본 데이터를 새 페이지로 복사
    - 쓰기를 시도한 프로세스의 페이지 테이블을 새 페이지를 가리키도록 업데이트
    - 쓰기 권한 복구
5. **명령 재실행**: 페이지 폴트에서 복귀하면 쓰기 명령이 성공적으로 실행됩니다

**COW의 효율성:**

- `fork()` 후 `exec()`로 새 프로그램을 로드하는 경우: 복사가 거의 일어나지 않아 매우 빠릅니다
- 프로세스가 대부분의 메모리를 읽기만 하는 경우: 물리 메모리를 공유하여 절약
- 실제로 수정되는 페이지만 복사: “필요할 때만” 비용 지불

### 가상 메모리와 페이지 테이블의 심층 구조

**가상 주소 공간의 구조 (64비트 시스템 기준):**

```
0x0000000000000000  ┌─────────────────┐
                    │   Reserved      │ (NULL 포인터 보호)
0x0000000000400000  ├─────────────────┤
                    │   .text (코드)  │ (읽기/실행, 공유 가능)
0x0000000000600000  ├─────────────────┤
                    │   .rodata       │ (읽기 전용 데이터)
0x0000000000800000  ├─────────────────┤
                    │   .data         │ (초기화된 전역 변수)
0x0000000000A00000  ├─────────────────┤
                    │   .bss          │ (초기화 안 된 전역)
0x0000000000C00000  ├─────────────────┤
                    │                 │
                    │   Heap ↓        │ (동적 할당, brk/mmap)
                    │                 │
                    │   (빈 공간)     │
                    │                 │
                    │   ↑ mmap 영역   │ (파일 매핑, 공유 라이브러리)
0x00007F0000000000  ├─────────────────┤
                    │   ↑ Stack       │ (지역 변수, 함수 호출)
0x00007FFFFFFFFFFF  └─────────────────┘
```

**페이지 테이블의 다단계 구조 (x86-64 4-Level Paging):**

64비트 가상 주소를 48비트로 축소하여 사용:

```
가상 주소 (48비트 사용):
[PML4 Index: 9비트][PDPT Index: 9비트][PD Index: 9비트][PT Index: 9비트][Offset: 12비트]
```

**주소 변환 과정:**

1. **CR3 레지스터**: 최상위 페이지 테이블(PML4)의 물리 주소 보관
2. **PML4 (Page Map Level 4)**: 첫 9비트로 512개 엔트리 중 하나 선택 → PDPT 주소
3. **PDPT (Page Directory Pointer Table)**: 다음 9비트로 PD 주소 획득
4. **PD (Page Directory)**: 다음 9비트로 PT 주소 획득
5. **PT (Page Table)**: 다음 9비트로 최종 물리 페이지 프레임 번호 획득
6. **물리 주소 생성**: 페이지 프레임 번호 + 하위 12비트 오프셋

**페이지 테이블 엔트리 (PTE)의 플래그들:**

- **Present (P)**: 페이지가 물리 메모리에 있는지 (0이면 페이지 폴트)
- **Read/Write (R/W)**: 쓰기 권한
- **User/Supervisor (U/S)**: 유저 모드 접근 가능 여부
- **Accessed (A)**: 페이지 접근 여부 (페이지 교체 알고리즘에 사용)
- **Dirty (D)**: 페이지 수정 여부 (스왑 아웃 시 디스크 기록 필요 판단)
- **NX (No Execute)**: 실행 금지 (보안: 버퍼 오버플로우 방지)

**TLB (Translation Lookaside Buffer)의 역할:**

- 메모리 4번 접근은 너무 비효율적 → TLB 캐시 사용
- 최근 사용된 가상→물리 주소 변환 결과를 저장
- TLB 히트 시: 단일 사이클로 주소 변환
- TLB 미스 시: 페이지 테이블 워킹 후 TLB 갱신
- 컨텍스트 스위칭 시: TLB 플러시 (프로세스마다 다른 주소 공간)

## 2단계: 스케줄러의 정교한 CPU 시간 관리

### 프로세스 상태와 전이

프로세스는 생애 동안 여러 상태를 거칩니다:

```
        fork()
          ↓
      [Created]
          ↓ 초기화 완료
      [Ready] ←──────────────┐
          ↓ 스케줄러 선택        │ I/O 완료, 인터럽트
      [Running] ──────────┐  │
          ↓               │  │
     타임 슬라이스 소진      │  │
          ↓               │  │
      [Ready] ←───────────┘  │
          ↓ I/O 요청          │
      [Waiting/Blocked] ─────┘
          ↓ exit()
      [Terminated]
```

### CFS (Completely Fair Scheduler)의 동작 원리

Linux의 기본 스케줄러인 CFS는 “완전히 공정한” CPU 시간 분배를 목표로 합니다:

**가상 런타임 (vruntime) 개념:**

- 각 프로세스가 “얼마나 CPU를 사용했는지” 추적하는 가상의 시간
- 실제 실행 시간을 프로세스의 우선순위로 가중하여 계산
- 공식: `vruntime += 실행시간 × (NICE_0_LOAD / 프로세스_가중치)`

**Red-Black Tree 자료구조:**

- 모든 실행 가능한 프로세스를 vruntime 순으로 정렬된 레드-블랙 트리에 저장
- 가장 왼쪽 노드 = vruntime이 가장 작은 프로세스 = 다음 실행 대상
- O(log N) 시간에 삽입/삭제 가능

**스케줄링 결정:**

1. 트리에서 가장 왼쪽 노드(최소 vruntime) 선택
2. 해당 프로세스에 CPU 할당
3. 타임 슬라이스 동안 실행 (보통 1~10ms)
4. 실행 후 vruntime 증가
5. 다시 트리에 삽입 (이제 오른쪽으로 이동했을 가능성 높음)
6. 반복

**우선순위 (Nice 값)의 영향:**

- Nice 값: -20 (최고 우선순위) ~ +19 (최저 우선순위)
- Nice 값이 낮을수록 가중치가 높아 vruntime 증가 속도가 느려짐
- 결과적으로 더 자주 스케줄링됨

**I/O 바운드 vs CPU 바운드 프로세스:**

- I/O 바운드: 자주 블록되어 vruntime이 천천히 증가 → 깨어날 때마다 높은 우선순위
- CPU 바운드: 계속 실행되어 vruntime 빠르게 증가 → 상대적으로 낮은 우선순위
- 자연스럽게 인터랙티브 프로세스(I/O 바운드)가 우선됨

### 컨텍스트 스위칭의 상세 과정

CPU를 프로세스 A에서 B로 전환할 때:

**1. 현재 상태 저장 (Process A):**

- 범용 레지스터 (RAX, RBX, RCX, RDX, RSI, RDI, RSP, RBP, R8-R15)
- 프로그램 카운터 (RIP)
- 스택 포인터 (RSP)
- 플래그 레지스터 (RFLAGS)
- FPU/SSE 상태 (부동소수점 레지스터)
- 세그먼트 레지스터들
- 위 정보를 PCB(Process Control Block)에 저장

**2. 스케줄러 결정:**

- 다음 실행할 프로세스 B 선택

**3. 메모리 컨텍스트 전환:**

- CR3 레지스터를 프로세스 B의 페이지 테이블 주소로 변경
- 이 순간 가상 주소 공간이 완전히 바뀜
- TLB 플러시 발생 (성능 비용 큼)

**4. 다음 상태 복원 (Process B):**

- PCB에서 모든 레지스터 값 복원
- 프로세스 B는 이전에 멈췄던 정확한 지점부터 재개

**5. 사용자 모드로 복귀:**

- 프로세스 B 실행 계속

**컨텍스트 스위칭 비용:**

- 직접 비용: 레지스터 저장/복원 (수십 나노초)
- 간접 비용: TLB/캐시 미스 증가 (수백 나노초~마이크로초)
- 너무 빈번하면 오버헤드, 너무 드물면 응답성 저하

## 3단계: 파일 시스템 - 논리적 데이터 조직

이제 프로세스가 파일을 생성하고 데이터를 쓰려 합니다:

```c
int fd = open("/home/user/data.txt", O_CREAT | O_WRONLY, 0644);
write(fd, "Hello, World!", 13);
```

### VFS (Virtual File System) - 통합 추상화 레이어

**VFS의 존재 이유:**

- 다양한 파일 시스템 (ext4, XFS, Btrfs, NTFS, FAT32, NFS 등)을 하나의 인터페이스로 통합
- 애플리케이션은 파일 시스템 종류를 몰라도 됨
- 새로운 파일 시스템 추가가 용이

**VFS의 핵심 객체들:**

1. **Superblock**:
    
    - 파일 시스템 전체의 메타데이터
    - 블록 크기, 총 블록 수, 마운트 정보 등
    - 각 마운트된 파일 시스템마다 하나씩 존재
2. **Inode (Index Node)**:
    
    - 개별 파일/디렉토리의 메타데이터
    - 파일 크기, 권한, 타임스탬프, 소유자, 그룹
    - 데이터 블록 위치 정보 (포인터들)
    - **중요**: 파일 이름은 inode에 없음! (디렉토리 엔트리에 있음)
3. **Dentry (Directory Entry)**:
    
    - 파일 이름과 inode 번호의 매핑
    - 디렉토리 구조를 표현
    - Dentry 캐시로 경로 탐색 가속화
4. **File Object**:
    
    - 열린 파일의 프로세스별 상태
    - 현재 파일 오프셋 (읽기/쓰기 위치)
    - 열기 모드 (읽기/쓰기/추가)

### 경로 이름 해석 (Path Name Resolution)

`/home/user/data.txt`를 찾는 과정:

**1. 루트부터 시작:**

- 루트 디렉토리(`/`)의 inode는 고정 (보통 inode #2)
- 루트 inode를 읽어 데이터 블록 위치 파악

**2. 디렉토리 순회:**

- 루트의 데이터 블록에서 “home” 엔트리 검색
- “home” → inode #1234 찾음
- inode #1234 읽어서 /home 디렉토리의 데이터 블록 위치 파악
- /home의 데이터 블록에서 “user” 엔트리 검색
- “user” → inode #5678 찾음
- inode #5678 읽어서 /home/user 디렉토리의 데이터 블록 위치 파악
- /home/user의 데이터 블록에서 “data.txt” 엔트리 검색

**3. 최종 파일 도달:**

- “data.txt” → inode #9999
- inode #9999가 우리가 원하는 파일의 메타데이터

**Dentry 캐시의 역할:**

- 최근 탐색한 경로를 메모리에 캐싱
- `/home/user/data.txt`를 이미 찾았다면, 다음 접근 시 디스크 I/O 없이 바로 inode 획득
- 경로가 길수록 캐시의 효과가 큼

### ext4 파일 시스템의 내부 구조

**디스크 레이아웃:**

```
┌──────────────────────────────────────────────────────────┐
│ Boot Block │ Block Group 0 │ Block Group 1 │ ... │ BG N │
└──────────────────────────────────────────────────────────┘
              │
              ↓
      ┌───────────────────────────────────────┐
      │ Superblock (파일시스템 전체 정보)      │
      ├───────────────────────────────────────┤
      │ Group Descriptors (각 그룹 메타데이터) │
      ├───────────────────────────────────────┤
      │ Block Bitmap (블록 사용 여부 추적)     │
      ├───────────────────────────────────────┤
      │ Inode Bitmap (inode 사용 여부 추적)    │
      ├───────────────────────────────────────┤
      │ Inode Table (실제 inode들)            │
      ├───────────────────────────────────────┤
      │ Data Blocks (실제 파일 데이터)         │
      └───────────────────────────────────────┘
```

**Inode 구조의 세부사항:**

```
Inode:
- 파일 모드 (권한 + 타입)
- 소유자 UID/GID
- 파일 크기 (바이트)
- 타임스탬프 (atime, mtime, ctime)
- 링크 카운트 (하드링크 개수)
- 블록 포인터 (Extent 기반):
  ┌─────────────────────┐
  │ Direct Extents (12개)│ → 작은 파일은 여기서 직접 처리
  ├─────────────────────┤
  │ Extent Tree Root     │ → 큰 파일은 B-Tree 구조로 관리
  └─────────────────────┘
```

**Extent (익스텐트) 방식:**

- 전통적인 블록 포인터 배열 대신 “연속된 블록 범위” 표현
- 형식: `(시작 블록 번호, 블록 개수)`
- 예: `(1000, 100)` = 블록 1000~1099까지 100개 블록이 연속
- 대용량 파일에서 메타데이터 크기 대폭 감소
- 단편화 감소

**파일 생성 시 (open with O_CREAT):**

1. 부모 디렉토리 inode 찾기
2. Inode Bitmap에서 빈 inode 할당
3. 새 inode 초기화 (권한, 소유자, 타임스탬프)
4. 부모 디렉토리의 데이터 블록에 새 엔트리 추가 (파일이름 → inode 매핑)
5. 부모 디렉토리의 mtime 갱신

**파일 쓰기 시 데이터 블록 할당:**

1. Block Bitmap에서 빈 블록(들) 찾기
2. 가능하면 연속된 블록 할당 (Extent 최적화)
3. Inode의 extent 트리에 새 블록 정보 추가
4. 실제 데이터를 블록에 기록
5. Inode의 파일 크기 갱신
6. Dirty 비트 설정 (저널링 대상)

### 저널링 (Journaling) - 일관성 보장

파일 시스템 작업 중 전원 차단 시 데이터 손상 방지:

**저널 모드:**

1. **Journal (메타데이터만)**:
    
    - 메타데이터 변경 사항만 저널에 기록
    - 성능과 안정성의 균형
    - ext4의 기본 모드
2. **Ordered**:
    
    - 데이터 블록을 먼저 쓰고, 그 후 메타데이터 저널링
    - 메타데이터가 가리키는 데이터가 항상 유효함 보장
3. **Writeback**:
    
    - 메타데이터와 데이터 쓰기 순서 보장 없음
    - 가장 빠르지만 안전성 낮음

**저널링 과정 (Ordered 모드):**

1. **데이터 블록 쓰기**: 실제 파일 데이터를 데이터 블록에 기록
2. **저널 시작**: 트랜잭션 시작 마커 기록
3. **메타데이터 저널 기록**: 변경할 메타데이터를 저널 영역에 기록
4. **커밋**: 트랜잭션 완료 마커 기록
5. **체크포인트**: 저널의 메타데이터를 실제 위치에 기록
6. **저널 해제**: 저널 공간 재사용 가능

**복구 시 (fsck):**

- 마지막 체크포인트 이후 커밋된 트랜잭션들을 재생(replay)
- 커밋 안 된 트랜잭션은 무시 (롤백)

## 4단계: 페이지 캐시 - 성능의 핵심

페이지 캐시는 파일 I/O 성능을 극적으로 향상시키는 메모리 캐시입니다.

### 페이지 캐시의 역할과 구조

**페이지 캐시란:**

- 파일의 내용을 메모리 페이지(보통 4KB)에 캐싱
- 커널이 관리하는 통합된 캐시
- 물리 메모리의 상당 부분을 차지 (유휴 메모리를 적극 활용)

**주소 공간 객체 (Address Space):**

- 각 파일의 inode는 address_space 구조체를 가짐
- 이 address_space가 해당 파일의 페이지 캐시를 관리
- Radix Tree(또는 XArray)로 구현: 파일 오프셋 → 메모리 페이지 매핑

```
파일 inode
    ↓
address_space
    ↓
Radix Tree (인덱스: 페이지 번호)
    ├─ [0] → 물리 페이지 (파일의 0~4KB)
    ├─ [1] → 물리 페이지 (파일의 4~8KB)
    ├─ [2] → 물리 페이지 (파일의 8~12KB)
    └─ ...
```

### 읽기 경로 (Read Path)

프로세스가 `read(fd, buffer, 4096)`를 호출하면:

**1. 시스템 콜 진입:**

- 유저 모드 → 커널 모드 전환
- VFS 레이어의 `vfs_read()` 호출

**2. 페이지 캐시 확인:**

- 파일의 address_space에서 해당 오프셋의 페이지 검색
- Radix Tree 조회로 O(log N) 시간

**3-A. 캐시 히트 (페이지가 메모리에 있음):**

- 메모리 페이지에서 사용자 버퍼로 데이터 복사
- 디스크 I/O 없음 → 매우 빠름 (마이크로초 단위)
- 페이지의 accessed 비트 설정 (LRU 알고리즘용)

**3-B. 캐시 미스 (페이지가 메모리에 없음):**

- **빈 페이지 할당**: 페이지 캐시에 새 페이지 추가
- **Read-Ahead (선행 읽기) 트리거**:
    - 순차 읽기 패턴 감지 시 다음 페이지들도 미리 읽어옴
    - 예: 4KB 요청 시 128KB까지 미리 읽기
    - 순차 읽기 성능 대폭 향상
- **블록 레이어에 I/O 요청**:
    - 파일 시스템이 파일 오프셋 → 블록 번호 변환
    - 블록 디바이스 드라이버에 읽기 요청
    - 프로세스는 **TASK_UNINTERRUPTIBLE** 상태로 대기
- **I/O 완료 후**:
    - 디스크에서 읽은 데이터를 페이지 캐시에 저장
    - 대기 중인 프로세스를 깨움 (TASK_RUNNING)
    - 페이지 캐시에서 사용자 버퍼로 복사

**Read-Ahead의 지능적 동작:**

- **순차 감지**: 연속된 오프셋 읽기 시 윈도우 크기 증가
- **랜덤 감지**: 불연속 읽기 시 선행 읽기 비활성화
- **적응적 크기**: 캐시 히트율에 따라 동적 조정

### 쓰기 경로 (Write Path)

프로세스가 `write(fd, buffer, 4096)`를 호출하면:

**1. 시스템 콜 진입:**

- VFS 레이어의 `vfs_write()` 호출

**2. 페이지 캐시 확인:**

- 해당 오프셋의 페이지를 캐시에서 찾음

**3. 페이지 준비:**

- **페이지가 캐시에 있으면**: 그 페이지 사용
- **페이지가 없으면**:
    - 새 페이지 할당
    - 부분 쓰기(페이지 전체가 아닌)인 경우: 먼저 디스크에서 읽어와야 함 (Read-Modify-Write)

**4. 메모리 쓰기:**

- 사용자 버퍼 → 페이지 캐시로 데이터 복사
- 페이지를 **Dirty**로 표시
- **write() 시스템 콜은 여기서 반환** (디스크 쓰기 전에!)

**5. Delayed Write (지연된 쓰기):**

- 실제 디스크 쓰기는 나중으로 미룸
- 이유:
    - **성능**: 여러 쓰기를 묶어서 한 번에 디스크에 기록
    - **수명**: SSD 쓰기 횟수 감소
    - **최적화**: 같은 블록을 여러 번 쓰면 마지막 것만 디스크에 기록

**6. Writeback (언제 디스크에 쓰나?):**

여러 트리거:

- **주기적 플러시**: pdflush/writeback 커널 스레드가 30초마다 실행
- **메모리 압박**: 페이지 캐시가 너무 커지면 dirty 페이지 먼저 기록
- **명시적 동기화**: `fsync()`, `sync()` 시스템 콜
- **파일 닫기**: `close()` 시 (보장은 아님)

**Writeback 과정:**

1. Dirty 페이지 목록 수집
2. 파일 시스템에 쓰기 요청 전달
3. 파일 시스템이 저널링 수행
4. 블록 레이어에 I/O 요청
5. 디바이스 드라이버가 실제 디스크 쓰기
6. 완료 후 Dirty 비트 제거

### 페이지 캐시 관리: 메모리 회수

**LRU (Least Recently Used) 리스트:**

- 페이지를 두 개의 LRU 리스트로 관리:
    - **Active List**: 최근에 두 번 이상 접근된 페이지
    - **Inactive List**: 한 번만 접근되었거나 오래된 페이지

**페이지 회수 과정 (kswapd 커널 스레드):**

1. **메모리 부족 감지**: 여유 메모리가 임계값 이하
2. **Inactive List 스캔**:
    - Referenced 비트가 0인 페이지 선택 (오래 안 쓴 것)
    - Dirty 페이지면 먼저 디스크에 기록
    - Clean 페이지면 즉시 해제
3. **Active → Inactive 이동**:
    - Active 리스트 하위에서 오래 안 쓴 페이지를 Inactive로 강등
4. **Second-Chance Algorithm**:
    - Referenced 비트가 1이면 0으로 바꾸고 리스트 뒤로 이동
    - 다음 스캔까지 또 접근되지 않으면 회수

**메모리 압박 시나리오:**

- 적당한 압박: kswapd가 백그라운드에서 천천히 회수
- 심각한 압박: 프로세스가 직접 회수 작업 수행 (Direct Reclaim) → 성능 저하

## 5단계: 블록 레이어 - I/O 스케줄링과 최적화

페이지 캐시 미스나 Writeback 시 실제 디스크 I/O가 필요합니다.

### 블록 레이어의 역할

**파일 시스템과 디바이스 드라이버 사이의 중간층:**

- 파일 시스템의 논리적 블록 → 물리적 디스크 섹터 변환
- 여러 I/O 요청을 효율적으로 정렬하고 병합
- I/O 우선순위 관리

### BIO (Block I/O) 구조체

개별 I/O 요청을 표현:

```
BIO:
- 디바이스 번호
- 시작 섹터 번호
- I/O 방향 (읽기/쓰기)
- 메모리 페이지 목록 (scatter-gather)
- 완료 시 콜백 함수
```

**Scatter-Gather I/O:**

- 물리적으로 불연속한 메모리 페이지들을 하나의 I/O 요청으로 묶음
- DMA 컨트롤러가 각 페이지를 순서대로 전송
- 시스템 콜 오버헤드 감소

### I/O 스케줄러

**역할**: 디스크 헤드 이동 최소화, 처리량 최대화, 지연 시간 공정성

**1. Deadline Scheduler:**

- 읽기/쓰기 요청을 별도 큐로 관리
- 읽기는 500ms, 쓰기는 5s 데드라인
- 데드라인 내에는 SCAN 알고리즘으로 정렬 (엘리베이터 방식)
- 데드라인 초과 시 우선 처리

**2. CFQ (Completely Fair Queuing):**

- 프로세스별로 별도 큐 유지
- Round-Robin으로 각 프로세스에게 I/O 타임 슬라이스 할당
- 한 프로세스가 I/O를 독점하지 못하게 방지

**3. NOOP:**

- SSD에 적합 (기계적 헤드 이동 없음)
- 단순히 요청을 FIFO로 처리
- 병합만 수행

**4. BFQ (Budget Fair Queueing):**

- 프로세스별 I/O 대역폭 공정 분배
- 인터랙티브 애플리케이션 우선순위 향상

**5. mq-deadline / Kyber (Multi-Queue):**

- NVMe SSD 시대의 스케줄러
- CPU 코어별 큐로 확장성 향상
- 락 경쟁 최소화

### Request 병합과 플러깅

**Request 병합:**

- 인접한 섹터에 대한 요청들을 하나로 합침
- 예: 섹터 100~107 읽기 + 섹터 108~115 읽기 → 섹터 100~115 하나의 요청

**플러깅 (Plugging):**

- 디바이스 큐를 잠시 "플러그"로 막아둠
- 짧은 시간(수 밀리초) 동안 요청을 모음
- 병합 기회 증가
- 언플러그 시 최적화된 순서로 한꺼번에 전송

## 6단계: 디바이스 드라이버 - 하드웨어와의 대화

### 디바이스 파일과 드라이버 등록

**디바이스 파일:**

```
$ ls -l /dev/sda
brw-rw---- 1 root disk 8, 0 Feb 12 10:30 /dev/sda
```

- `b`: 블록 디바이스
- `8`: major number (SCSI 디스크 드라이버)
- `0`: minor number (첫 번째 디스크)

**드라이버 등록:**

1. 드라이버가 커널에 로드될 때 `register_blkdev()` 호출
2. Major number 할당 받음
3. 디바이스 감지 시 minor number 할당하여 디바이스 노드 생성
4. `block_device_operations` 구조체 등록 (함수 포인터 테이블)

### 드라이버의 요청 처리 흐름

**1. Request Queue에서 요청 수신:**

- I/O 스케줄러가 최적화한 요청을 드라이버에 전달

**2. 하드웨어 명령어 생성:**

- SATA/AHCI: ATA 명령어 생성 (예: READ DMA EXT, WRITE DMA EXT)
- NVMe: NVMe 명령어 생성 (Submission Queue Entry)
- 명령어 구조:
    - 커맨드 코드 (읽기/쓰기)
    - LBA (Logical Block Address)
    - 섹터 수
    - DMA 메모리 주소

**3. DMA (Direct Memory Access) 설정:**

- 드라이버가 물리 메모리 주소를 디바이스에 전달
- 주소 변환 주의: 커널 가상 주소 → 물리 주소 (virt_to_phys)
- IOMMU가 있다면: 디바이스용 가상 주소 → 물리 주소 변환

**DMA의 장점:**

- CPU 개입 없이 디바이스가 직접 메모리 접근
- CPU는 다른 작업 수행 가능
- 대용량 전송 시 효율적

**4. 명령 전송:**

- MMIO를 통해 디바이스 레지스터에 명령 기록

## 7단계: MMIO와 하드웨어 제어

### MMIO (Memory-Mapped I/O) 상세

**물리 주소 공간의 구성:**

```
0x00000000  ┌─────────────────┐
            │                 │
            │   System RAM    │
            │   (예: 16GB)    │
            │                 │
0x3FFFFFFFF ├─────────────────┤  ← RAM 끝
            │   Reserved      │
0xE0000000  ├─────────────────┤  ← PCIe 설정 공간
            │                 │
            │  MMIO Region    │
            │                 │
            │ - GPU (1GB)     │
            │ - NVMe (64KB)   │
            │ - SATA (8KB)    │
            │ - USB (4KB)     │
            │                 │
0xFFFFFFFF  └─────────────────┘
```

**BAR (Base Address Register):**

- PCI/PCIe 디바이스는 BAR를 통해 MMIO 영역 요청
- 커널이 BAR를 읽어 MMIO 주소 파악
- 드라이버가 `ioremap()`으로 가상 주소에 매핑

**MMIO 접근 예시:**

```c
void __iomem *base = ioremap(0xFE200000, 0x1000);  // 4KB 매핑
uint32_t status = ioread32(base + OFFSET_STATUS);  // 읽기
iowrite32(COMMAND_START, base + OFFSET_COMMAND);   // 쓰기
```

**왜 ioread/iowrite를 쓰나?**

- 컴파일러의 최적화 방지
- Memory barrier 보장 (순서 유지)
- 아키텍처별 차이 추상화

### 레지스터 구조 예시 (NVMe 컨트롤러)

```
Offset  | 레지스터         | 설명
--------|------------------|---------------------------
0x0000  | CAP (Capability) | 컨트롤러 능력 (읽기 전용)
0x0008  | VS (Version)     | NVMe 버전
0x0014  | CC (Config)      | 컨트롤러 설정 (읽기/쓰기)
0x001C  | CSTS (Status)    | 컨트롤러 상태
0x0024  | AQA              | Admin Queue 속성
0x0028  | ASQ              | Admin Submission Queue 주소
0x0030  | ACQ              | Admin Completion Queue 주소
0x1000+ | Doorbell         | Submission Queue 알림
```

**명령 전송 과정:**

1. Submission Queue에 명령 작성 (메모리)
2. Doorbell 레지스터에 쓰기 (MMIO) → 디바이스에 “새 명령 있음” 알림
3. 디바이스가 Submission Queue에서 명령 읽어감 (DMA)
4. 작업 수행
5. Completion Queue에 결과 기록 (DMA)
6. 인터럽트 발생

## 8단계: 폴링 vs 인터럽트 vs 혼합

### 폴링 (Polling)

**동작:**

```c
while (!(ioread32(status_reg) & DONE_BIT)) {
    cpu_relax();  // 잠깐 쉬기
}
```

**특징:**

- 매우 낮은 지연 시간 (수십 마이크로초)
- CPU 코어 하나를 100% 소비
- 고속 NVMe SSD에 유리 (완료까지 수백 마이크로초)

**사용 사례:**

- 고성능 트레이딩 시스템
- 실시간 데이터 수집
- 지연 시간이 극도로 중요한 애플리케이션

### 인터럽트 (Interrupt)

**동작 흐름:**

1. **드라이버가 명령 전송 후:**
    
    - 현재 프로세스를 대기 큐에 넣음
    - 프로세스 상태 = TASK_UNINTERRUPTIBLE (또는 TASK_INTERRUPTIBLE)
    - `schedule()` 호출 → 다른 프로세스에게 CPU 양보
2. **디바이스 작업 완료:**
    
    - 디바이스가 MSI-X 인터럽트 발생
    - CPU의 APIC (Advanced Programmable Interrupt Controller)가 수신
    - 현재 실행 중인 프로세스 중단
3. **인터럽트 핸들러 (Top Half):**
    
    - 매우 빠르게 실행되어야 함 (마이크로초 단위)
    - 디바이스 상태 레지스터 읽기
    - 인터럽트 확인 응답 (ACK)
    - Completion Queue에서 결과 읽기
    - Softirq 또는 Tasklet 스케줄링
4. **Softirq / Tasklet (Bottom Half):**
    
    - 인터럽트 컨텍스트가 아닌 더 느슨한 환경에서 실행
    - 무거운 처리: 데이터 복사, 페이지 캐시 업데이트 등
    - 대기 중인 프로세스 깨우기 (wake_up)
5. **프로세스 재개:**
    
    - 스케줄러가 깨어난 프로세스를 Ready 큐에 추가
    - 다음 스케줄링 시점에 CPU 할당
    - 프로세스는 시스템 콜에서 반환

**인터럽트 종류:**

- **Legacy INTx**: 옛날 방식, 공유 인터럽트 라인 (비효율적)
- **MSI (Message Signaled Interrupts)**: PCIe 메모리 쓰기로 인터럽트 전달
- **MSI-X**: 여러 인터럽트 벡터 지원, CPU 코어별 분산 가능

**MSI-X의 장점:**

- 디바이스가 여러 큐를 가지면 각 큐마다 다른 CPU 코어에 인터럽트
- NUMA 시스템에서 지역성 향상
- 확장성 우수

### 혼합 방식: Hybrid Polling

**Intel의 “Busy Polling”:**

- I/O 제출 직후 짧은 시간(수십 마이크로초) 동안 폴링
- 완료되지 않으면 인터럽트 모드로 전환
- 짧은 지연 시간의 I/O는 폴링으로, 긴 I/O는 인터럽트로 자동 선택

**io_uring의 IORING_SETUP_IOPOLL:**

- 유저 공간이 직접 Completion Queue를 폴링
- 커널 전환 없이 완료 확인
- 극한의 성능 요구 애플리케이션용

## 9단계: 전체 흐름 통합 - 실제 시나리오

이제 모든 요소를 하나로 엮어봅시다. 프로세스가 파일을 읽는 전체 여정:

### 시나리오: 100MB 로그 파일 읽기

```c
int fd = open("/var/log/app.log", O_RDONLY);
char buffer[4096];
read(fd, buffer, 4096);
```

**Step 1: 프로세스 생성과 스케줄링**

- 쉘이 `fork()`로 프로세스 생성 → COW로 페이지 테이블만 복사
- `exec()`로 프로그램 로드 → 코드 페이지는 파일에서 demand paging
- 프로세스가 Ready 큐에 들어가고 CFS 스케줄러가 CPU 할당

**Step 2: open() 시스템 콜**

- User mode → Kernel mode 전환 (syscall 명령)
- VFS의 `do_sys_open()` 호출
- 경로 해석:
    - `/` → inode #2 (Dentry 캐시 히트)
    - `/var` → inode #256 (Dentry 캐시 히트)
    - `/var/log` → inode #512 (Dentry 캐시 히트)
    - `/var/log/app.log` → inode #9999 (Dentry 캐시 미스)
        - 디스크에서 `/var/log` 디렉토리의 데이터 블록 읽기 (페이지 캐시 통해)
        - “app.log” → inode #9999 찾음
        - Dentry 캐시에 추가
- inode #9999의 권한 검사 (읽기 권한 확인)
- File 구조체 생성:
    - inode 포인터 = #9999
    - 파일 오프셋 = 0
    - 모드 = O_RDONLY
- 파일 디스크립터 테이블에 추가 (fd = 3)
- Kernel mode → User mode 복귀, fd=3 반환

**Step 3: read() 시스템 콜**

- User mode → Kernel mode 전환
- VFS의 `vfs_read()` 호출
- `generic_file_read_iter()` → 페이지 캐시 기반 읽기

**Step 4: 페이지 캐시 조회**

- 파일 오프셋 0 → 페이지 번호 0 (0~4KB)
- inode #9999의 address_space에서 페이지 0 검색
- **시나리오 A: 캐시 미스** (처음 읽기)

**Step 5: 페이지 할당 및 I/O 준비**

- 페이지 캐시에 새 물리 페이지 할당
- address_space의 Radix Tree에 추가 (페이지 0 → 물리 페이지)
- Read-ahead 트리거: 페이지 1~31도 함께 읽기로 결정 (128KB)

**Step 6: 파일 시스템 레이어 (ext4)**

- Extent 트리에서 파일 오프셋 0~128KB → 디스크 블록 번호 변환
- 예: 블록 #500000~#500031 (연속된 32개 블록)
- BIO 구조체 생성:
    - 디바이스: /dev/sda1
    - 시작 섹터: 4000000 (블록 500000 × 8 섹터/블록)
    - 섹터 수: 256 (32블록 × 8)
    - 메모리 페이지: 페이지 0~31 (scatter-gather 리스트)

**Step 7: 블록 레이어**

- BIO를 request로 감싸기
- I/O 스케줄러에 제출 (예: mq-deadline)
- 기존 요청과 병합 가능 여부 확인
- Request Queue에 삽입 (섹터 번호 순으로 정렬)
- 짧은 플러깅 (수 밀리초)
- 언플러그 → 드라이버에 요청 전달

**Step 8: 디바이스 드라이버 (AHCI/SATA)**

- Request Queue에서 요청 가져옴
- ATA READ DMA EXT 명령 생성:
    - LBA: 4000000
    - 섹터 수: 256
    - Feature 레지스터 설정
- DMA 설정:
    - PRD (Physical Region Descriptor) 테이블 생성
    - 각 페이지의 물리 주소와 크기 기록
    - PRD 테이블의 물리 주소를 컨트롤러에 전달
- 프로세스를 대기 큐에 추가 (I/O wait)
- 프로세스 상태 = TASK_UNINTERRUPTIBLE
- `schedule()` 호출 → 스케줄러가 다른 프로세스에 CPU 할당

**Step 9: MMIO를 통한 명령 전달**

- SATA 컨트롤러의 MMIO 주소: 0xFE400000
- 드라이버가 레지스터에 기록:
    
    ```
    [0xFE400000 + 0x00] = LBA (하위 24비트)
    [0xFE400000 + 0x04] = LBA (상위 24비트) + 섹터 수
    [0xFE400000 + 0x08] = 명령 레지스터 (READ DMA EXT)
    [0xFE400000 + 0x0C] = PRD 테이블 주소
    [0xFE400000 + 0x10] = 시작 비트 설정
    ```
    

**Step 10: 디스크 작업**

- SATA 컨트롤러가 명령 수신
- 디스크에 ATA 명령 전달
- 디스크 헤드 이동 (HDD라면) 또는 플래시 셀 읽기 (SSD라면)
- 수 밀리초 소요 (HDD: 5~15ms, SATA SSD: 0.1~0.5ms, NVMe SSD: 0.02~0.1ms)
- 데이터를 내부 버퍼에 로드
- DMA 전송 시작:
    - PRD 테이블의 첫 번째 엔트리 읽기
    - 해당 물리 메모리 주소에 데이터 쓰기
    - 다음 PRD 엔트리로 계속
    - 256 섹터 (128KB) 모두 전송

**Step 11: 인터럽트 발생**

- 디스크 컨트롤러가 MSI-X 인터럽트 전송
- CPU의 로컬 APIC가 수신
- 현재 실행 중이던 프로세스 B 중단 (레지스터 저장)
- IDT (Interrupt Descriptor Table)에서 핸들러 주소 조회
- SATA 드라이버의 인터럽트 핸들러 실행

**Step 12: 인터럽트 핸들러 (Top Half)**

- AHCI 포트 상태 레지스터 읽기 (MMIO)
- 완료된 명령 슬롯 확인
- 인터럽트 클리어 (ACK)
- Softirq 스케줄링 (BLOCK_SOFTIRQ)
- 핸들러 종료 (수 마이크로초 소요)

**Step 13: Softirq (Bottom Half)**

- ksoftirqd 커널 스레드 또는 인터럽트 복귀 시 실행
- BIO 완료 콜백 호출
- 페이지 캐시 페이지들을 uptodate로 표시
- 대기 큐에서 프로세스 A 깨우기 (wake_up)
- 프로세스 A 상태 = TASK_RUNNING
- Ready 큐에 추가

**Step 14: 프로세스 재개**

- 스케줄러가 프로세스 A 선택 (vruntime이 작아서 우선순위 높음)
- 컨텍스트 스위칭:
    - 프로세스 B 상태 저장
    - CR3 레지스터를 프로세스 A의 페이지 테이블로 변경
    - TLB 플러시
    - 프로세스 A 레지스터 복원
- 프로세스 A는 `schedule()` 이후부터 재개

**Step 15: 데이터 복사**

- 페이지 캐시의 페이지 0에서 사용자 버퍼로 4KB 복사
- `copy_to_user()`: 커널 공간 → 유저 공간
- 페이지 폴트 가능성 (사용자 버퍼 페이지가 스왑 아웃되었다면)
- 파일 오프셋 4096으로 증가
- `read()` 시스템 콜 반환값 = 4096

**Step 16: 커널 모드 복귀**

- Kernel mode → User mode 전환
- 사용자 프로그램은 `read()` 다음 줄부터 계속 실행

**후속 읽기 (페이지 1~31):**

- 다음 `read()` 호출 시 페이지 캐시 히트
- 디스크 I/O 없이 메모리 복사만
- 수십 마이크로초 만에 완료

### 쓰기 시나리오: 파일에 1MB 데이터 쓰기

```c
int fd = open("/home/user/output.dat", O_WRONLY | O_CREAT, 0644);
char data[1048576];  // 1MB
write(fd, data, 1048576);
fsync(fd);  // 명시적 동기화
```

**단계별 흐름:**

**1. open() - 파일 생성:**

- 경로 해석으로 `/home/user` 디렉토리의 inode 찾기
- Inode Bitmap에서 빈 inode 할당 (예: #12345)
- 새 inode 초기화:
    - 모드: 0644 (rw-r–r–)
    - UID/GID: 현재 프로세스
    - 크기: 0
    - 타임스탬프: 현재 시간
    - Extent 트리: 비어 있음
- `/home/user` 디렉토리에 엔트리 추가: `"output.dat" → inode #12345`
- 저널에 메타데이터 변경 기록 (트랜잭션)
- File 구조체 생성 및 fd 반환

**2. write() - 페이지 캐시 쓰기:**

- 1MB = 256 페이지 (4KB × 256)
- 각 페이지마다:
    - 페이지 캐시에 새 페이지 할당
    - 사용자 데이터를 페이지에 복사 (`copy_from_user`)
    - 페이지를 Dirty로 표시
    - address_space의 Radix Tree에 추가
- inode의 파일 크기를 1MB로 업데이트
- **write() 시스템 콜은 여기서 반환** (디스크 미기록 상태)

**3. fsync() - 강제 동기화:**

- VFS의 `do_fsync()` 호출
- 파일의 모든 dirty 페이지를 디스크에 기록하도록 트리거

**4. Writeback 시작:**

- 256개의 dirty 페이지 수집
- ext4 파일 시스템이 블록 할당:
    - Block Bitmap에서 256개의 연속 블록 찾기 (예: 블록 #600000~#600255)
    - Extent 생성: `(600000, 256)`
    - inode의 extent 트리에 추가
- 저널링:
    - 메타데이터 변경(extent 추가, 파일 크기)을 저널에 기록
    - 트랜잭션 커밋

**5. BIO 제출:**

- 256 페이지에 대한 BIO 생성
- 블록 레이어에 제출
- I/O 스케줄러가 정렬 및 병합
- 디바이스 드라이버에 전달

**6. DMA 쓰기:**

- ATA WRITE DMA EXT 명령 생성
- PRD 테이블로 256개 페이지의 물리 주소 전달
- MMIO로 명령 전송
- 디스크가 1MB 데이터를 DMA로 가져가서 기록

**7. 인터럽트 및 완료:**

- 쓰기 완료 후 인터럽트
- 핸들러가 dirty 비트 제거
- 저널 체크포인트: 저널의 메타데이터를 실제 위치에 기록
- `fsync()` 시스템 콜 반환

**fsync() 없었다면?:**

- dirty 페이지는 최대 30초 동안 메모리에만 존재
- 그 사이 전원 차단 시 데이터 손실
- `fsync()`는 지속성 보장

## 핵심 연결 포인트 총정리

### 1. 프로세스 ↔ 가상 메모리

- **COW**: 프로세스 생성 시 메모리 효율성
- **페이지 테이블**: 가상 주소 → 물리 주소 변환
- **TLB**: 변환 결과 캐싱으로 성능 향상
- **페이지 폴트**: Demand paging, COW 실현, 스왑

### 2. 스케줄러 ↔ 모든 것

- **프로세스 상태 전이**: Running ↔ Ready ↔ Waiting
- **I/O 대기**: 블록 시 다른 프로세스 실행 → CPU 효율
- **CFS**: 공정한 CPU 시간 분배, I/O 바운드 우대
- **컨텍스트 스위칭**: 페이지 테이블 전환, TLB 플러시

### 3. 페이지 캐시 ↔ 파일 시스템

- **통합 캐시**: 모든 파일 I/O의 중앙 허브
- **지연 쓰기**: 성능 최적화, 여러 쓰기 통합
- **Read-ahead**: 순차 읽기 성능 향상
- **메모리 압박 시**: Dirty 페이지 먼저 writeback

### 4. 파일 시스템 ↔ 블록 레이어

- **논리 → 물리**: 파일 오프셋 → 디스크 블록 번호
- **Extent**: 연속 블록을 효율적으로 표현
- **저널링**: 메타데이터 일관성 보장
- **BIO**: 블록 레이어의 I/O 요청 단위

### 5. 블록 레이어 ↔ 드라이버

- **I/O 스케줄링**: 디스크 헤드 이동 최소화
- **병합 & 플러깅**: 요청 묶기로 효율 향상
- **Multi-queue**: NVMe 시대의 확장성

### 6. 드라이버 ↔ 하드웨어

- **MMIO**: 메모리 주소로 레지스터 접근
- **DMA**: CPU 부담 없이 대용량 전송
- **MSI-X**: 효율적인 인터럽트, 코어별 분산

### 7. 인터럽트 ↔ 스케줄러

- **비동기 I/O**: 완료 시 프로세스 깨우기
- **Top/Bottom Half**: 빠른 ACK + 무거운 처리 분리
- **I/O wait → Ready**: 스케줄러가 재실행

## 성능 최적화의 핵심

1. **계층적 캐싱**:
    
    - TLB → 페이지 테이블
    - 페이지 캐시 → 디스크
    - Dentry 캐시 → 파일 시스템
2. **비동기 처리**:
    
    - I/O 대기 중 다른 작업 실행
    - 지연 쓰기로 빠른 응답
3. **배치 처리**:
    
    - I/O 병합 및 플러깅
    - Writeback에서 여러 페이지 한꺼번에
4. **지연 로딩**:
    
    - COW의 지연 복사
    - Demand paging
    - Read-ahead의 추측 로딩
5. **공정성과 우선순위**:
    
    - CFS로 CPU 시간 분배
    - I/O 스케줄러로 디스크 대역폭 분배
    - 인터랙티브 작업 우대
