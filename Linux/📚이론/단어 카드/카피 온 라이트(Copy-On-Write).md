> [!정리]
> COW는 **읽기 위주, 생성이 잦은 환경에서는 매우 효율적**이지만  
**쓰기 중심 워크로드에서는 병목이 될 수 있는 기법**입니다.
### 1. 기본 개념

카피 온 라이트는 **메모리를 즉시 복사하지 않고**,  
**쓰기(write)가 발생하는 시점에만 실제 복사를 수행**하는 메모리 최적화 기법이다.

- 읽기만 하는 동안: 메모리 공유
    
- 쓰기가 발생하면: 해당 페이지만 복사
    

---

### 2. 왜 필요한가

프로세스를 생성할 때(특히 `fork()`):

- 부모 프로세스의 메모리를
    
- 자식 프로세스에게 그대로 복사하면
    
    - 비용이 매우 큼
        
    - 대부분의 경우 곧 `exec()`으로 덮어씀
        

COW는 이 **불필요한 메모리 복사 비용**을 제거한다.

---

### 3. `fork()`에서의 COW 동작 흐름 ⭐

##### 표기 규칙

```
VAx : 가상 주소 페이지
PAx : 물리 주소 페이지
R/O : Read Only
R/W : Read / Write
```

#### 1. 초기 상태 (fork() 호출 직후)

##### 가상 주소 공간

```
부모 프로세스 VA 공간
VA1  VA2  VA3  ...

자식 프로세스 VA 공간
VA1  VA2  VA3  ...
```

- 부모와 자식은 **완전히 동일한 가상 주소 공간 레이아웃**을 가짐
    
- 가상 주소의 개수, 배치, 주소 값 모두 동일
    

##### 가상 주소 → 물리 주소 매핑

```
부모 VA2 ──┐
            ├─→ PA2 (R/O)
자식 VA2 ──┘
```

- 부모와 자식의 페이지 테이블은
    
    - 동일한 가상 페이지(VA2)를
        
    - 동일한 물리 페이지(PA2)에 매핑
        
- 해당 페이지는 **읽기 전용(Read-Only)** 으로 설정됨
    

#### 2. 쓰기 시도 발생

```
부모 프로세스가 VA2에 쓰기 시도
            ↓
Write Protection Page Fault 발생
```

- 읽기 전용으로 표시된 페이지에 쓰기를 시도
    
- CPU가 페이지 폴트를 발생
    
- 커널 모드로 전환됨
    

#### 3. 커널 처리 (Copy-on-Write 동작)

##### 물리 메모리 분리

```
부모 VA2 ──→ PA2' (R/W)   ← 새로 할당된 물리 페이지
자식 VA2 ──→ PA2  (R/O)   ← 기존 물리 페이지 유지
```

커널이 수행하는 작업은 다음과 같다.

1. **새로운 물리 페이지 PA2' 할당**
    
2. **쓰기 작업을 시도한 페이지의 내용만 복사**
    
    - 전체 메모리 영역이 아니라
        
    - 문제를 일으킨 **해당 페이지 하나만 복사**
        
3. **쓰기 작업을 시도한 프로세스의 페이지 테이블만 수정**
    
    - 부모 프로세스의 PTE에서
        
        - VA2 → PA2 매핑을
            
        - VA2 → PA2' 로 변경
            
    - 페이지 권한을 **Read/Write**로 변경
        

#### 4. 가상 주소 관점에서의 변화

```
부모 VA 공간
VA1  VA2  VA3  ...

자식 VA 공간
VA1  VA2  VA3  ...
```

- **가상 주소 공간은 전혀 변하지 않음**
    
- fork 전후, COW 처리 전후 모두 동일
    
- 변경은 오직 **물리 페이지 매핑 관계**에서만 발생
    

#### 5. 핵심 정리

- Copy-on-Write에서
    
    - 복사되는 것은 **물리 메모리 페이지**
        
    - 유지되는 것은 **가상 주소 공간**
        
- 페이지 테이블 엔트리의 개수는 변하지 않으며
    
    - **해당 가상 페이지에 대응하는 PTE 하나만 수정됨**
        
- 상대 프로세스의 페이지 테이블은 수정되지 않음
    
- 전체 페이지 테이블이나 메모리 영역 복사는 발생하지 않음
    

#### 정리 문장 (면접용 한 문장)

> `fork()` 이후 부모와 자식은 동일한 가상 주소 공간을 유지한 채 물리 페이지를 읽기 전용으로 공유하고,  
> 쓰기 시도가 발생하면 커널은 해당 가상 페이지에 대해서만 새로운 물리 페이지를 할당한 뒤  
> **쓰기 작업을 시도한 프로세스의 페이지 테이블 엔트리만 수정한다.**

---

### 4. 페이지 테이블 관점

- fork 직후
    
    - 부모·자식의 PTE는
        
        - 동일한 물리 페이지를 가리킴
            
        - 쓰기 금지 플래그 설정
            
- 쓰기 발생 시
    
    - 한쪽 프로세스의 PTE만
        
        - 새 물리 페이지로 변경
            
        - 쓰기 허용
            

다른 프로세스는 여전히 기존 페이지를 공유한다.

---

### 5. Demand Paging과의 관계

COW는 **페이지 폴트 기반 메커니즘**이다.

- Demand Paging
    
    - “아직 물리 메모리가 없는 페이지 접근”
        
- Copy-on-Write
    
    - “물리 메모리는 있지만 쓰기 권한이 없는 페이지 접근”
        

둘 다:

- 페이지 폴트를 정상적인 처리 흐름으로 사용한다.
    

---

### 6. Huge Page와의 관계 (중요 포인트)

- Huge Page는
    
    - 크기가 크기 때문에
        
    - COW 발생 시 복사 비용이 매우 큼
        
- 이 때문에:
    
    - THP는 COW 상황에서
        
        - Huge Page를 쪼개서(split)
            
        - 일반 4KB 페이지로 되돌리는 경우가 많다.
            

즉:

- COW와 Huge Page는
    
    - 항상 잘 맞는 조합은 아니다.
        

---

### 7. 장점과 비용

#### 장점

- fork 성능 대폭 향상
    
- 메모리 사용량 절감
    
- 불필요한 복사 제거
    

#### 비용

- 첫 쓰기 시 페이지 폴트 발생
    
- 쓰기 집중 워크로드에서는 복사 비용 증가
    

---

### 8. 한 문장 요약

카피 온 라이트는 여러 프로세스가 메모리를 공유하다가, 쓰기가 발생하는 순간에만 해당 페이지를 복사함으로써 메모리와 성능을 효율적으로 사용하는 기법이다.
