## 카피 온 라이트 (Copy-on-Write, COW)

### 1. 기본 개념

카피 온 라이트는 **메모리를 즉시 복사하지 않고**,  
**쓰기(write)가 발생하는 시점에만 실제 복사를 수행**하는 메모리 최적화 기법이다.

- 읽기만 하는 동안: 메모리 공유
    
- 쓰기가 발생하면: 해당 페이지만 복사
    

---

### 2. 왜 필요한가

프로세스를 생성할 때(특히 `fork()`):

- 부모 프로세스의 메모리를
    
- 자식 프로세스에게 그대로 복사하면
    
    - 비용이 매우 큼
        
    - 대부분의 경우 곧 `exec()`으로 덮어씀
        

COW는 이 **불필요한 메모리 복사 비용**을 제거한다.

---

### 3. `fork()`에서의 COW 동작 흐름

1. `fork()` 호출
    
2. 부모와 자식 프로세스는
    
    - **같은 물리 메모리 페이지를 공유**
        
3. 해당 페이지들은
    
    - **읽기 전용(read-only)** 으로 표시됨
        
4. 부모 또는 자식이 페이지에 **쓰기 시도**
    
5. 쓰기 보호로 인해 **페이지 폴트 발생**
    
6. 커널이
    
    - 새로운 물리 페이지를 할당
        
    - 기존 내용을 복사
        
    - 해당 프로세스의 페이지 테이블만 수정
        
7. 이후 쓰기는 복사된 페이지에 수행
    

---

### 4. 페이지 테이블 관점

- fork 직후
    
    - 부모·자식의 PTE는
        
        - 동일한 물리 페이지를 가리킴
            
        - 쓰기 금지 플래그 설정
            
- 쓰기 발생 시
    
    - 한쪽 프로세스의 PTE만
        
        - 새 물리 페이지로 변경
            
        - 쓰기 허용
            

다른 프로세스는 여전히 기존 페이지를 공유한다.

---

### 5. Demand Paging과의 관계

COW는 **페이지 폴트 기반 메커니즘**이다.

- Demand Paging
    
    - “아직 물리 메모리가 없는 페이지 접근”
        
- Copy-on-Write
    
    - “물리 메모리는 있지만 쓰기 권한이 없는 페이지 접근”
        

둘 다:

- 페이지 폴트를 정상적인 처리 흐름으로 사용한다.
    

---

### 6. Huge Page와의 관계 (중요 포인트)

- Huge Page는
    
    - 크기가 크기 때문에
        
    - COW 발생 시 복사 비용이 매우 큼
        
- 이 때문에:
    
    - THP는 COW 상황에서
        
        - Huge Page를 쪼개서(split)
            
        - 일반 4KB 페이지로 되돌리는 경우가 많다.
            

즉:

- COW와 Huge Page는
    
    - 항상 잘 맞는 조합은 아니다.
        

---

### 7. 장점과 비용

#### 장점

- fork 성능 대폭 향상
    
- 메모리 사용량 절감
    
- 불필요한 복사 제거
    

#### 비용

- 첫 쓰기 시 페이지 폴트 발생
    
- 쓰기 집중 워크로드에서는 복사 비용 증가
    

---

### 8. 한 문장 요약

카피 온 라이트는 여러 프로세스가 메모리를 공유하다가, 쓰기가 발생하는 순간에만 해당 페이지를 복사함으로써 메모리와 성능을 효율적으로 사용하는 기법이다.
