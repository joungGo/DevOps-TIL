## 🏁 시작하기 전에 — 배경 지식

### 쿠버네티스(Kubernetes)란?

여러 대의 서버(노드)를 하나의 클러스터로 묶어 **컨테이너를 자동으로 배포하고 관리해주는 시스템**입니다.  
여러 대의 서버가 하나의 큰 컴퓨터처럼 움직이며, CPU·메모리를 **공유 풀(pool)** 처럼 사용합니다.

### 파드(Pod)와 컨테이너(Container)란?

- **컨테이너**: 독립적인 실행 환경이 있는 앱의 최소 단위 (도커 컨테이너라고도 함)
- **파드**: 쿠버네티스에서 컨테이너를 담는 껍데기. 1개 이상의 컨테이너를 포함할 수 있음

### cgroup이란?

> 리눅스 커널의 기능으로, **각 프로세스(컨테이너)가 사용할 수 있는 CPU·메모리 등을 제한하는 기술**입니다.  
> 도커와 쿠버네티스 모두 내부적으로 cgroup을 이용해 리소스를 통제합니다.

## 📦 1. 리소스 사용량 제한 — `limits`와 `requests`

### 왜 제한이 필요할까?

별도 설정이 없으면 파드는 **노드(서버)의 자원을 무제한으로 사용**할 수 있습니다.  
한 파드가 CPU·메모리를 독점하면 같은 서버에 있는 다른 파드들이 죽어버릴 수 있어요.

```
💡 비유: 기숙사 공용 인터넷
   한 학생이 대용량 파일을 다운로드하면 다른 학생들이 인터넷을 못 쓰는 상황
   → 각자 최대 사용량을 제한해야 함!
```

### `limits` — 최대 사용량 제한

컨테이너가 **절대 넘어서는 안 되는 최대치**를 정합니다.

```yaml
resources:
  limits:
    cpu: "1000m"      # CPU 1코어 (1000m = 1core)
    memory: "250Mi"   # 메모리 약 250MB
```

|단위|의미|
|---|---|
|`1000m`|CPU 1코어 (밀리코어: 1/1000 단위)|
|`500m`|CPU 0.5코어|
|`Mi`|Mebibyte ≈ MB (250Mi ≈ 262MB)|
|`Gi`|Gibibyte ≈ GB|

### `requests` — 최소 보장량 (스케줄링 기준!)

**“이 정도는 반드시 보장해줘”** 라는 의미입니다.  
쿠버네티스 스케줄러는 **requests를 기준으로** 파드를 어느 노드에 배치할지 결정합니다.

```yaml
resources:
  limits:
    cpu: "1000m"
    memory: "256Mi"
  requests:
    cpu: "500m"      # 최소 0.5코어 보장
    memory: "128Mi"  # 최소 128Mi 보장
```

> 🔑 **핵심 요약**
> 
> - `requests` = 파드 배치 기준 + 최소 보장량
> - `limits` = 절대 넘으면 안 되는 최대치

## 🔄 2. 오버커밋(Overcommit) — 유휴 자원 활용하기

### 문제 상황

아래처럼 총 1GB 메모리를 가진 노드에 2개의 컨테이너가 있다고 가정해봅시다.

```
노드 총 메모리: 1GB
┌───────────────────────────────────┐
│  컨테이너 A  │  컨테이너 B        │
│  할당: 500MB  │  할당: 500MB       │
│  사용: 50MB ← │  사용: 500MB ← 꽉 참│
│  450MB 낭비!!  │                   │
└───────────────────────────────────┘
```

**A가 450MB를 안 쓰고 있는데, B에게 줄 수 없을까요?** → 이게 바로 오버커밋!

### 오버커밋이란?

**실제 물리적 자원보다 더 많은 양을 파드에 할당**해서, 유휴 자원을 다른 파드가 임시로 빌려 쓸 수 있게 하는 기법입니다.

```
비유: 항공사 초과 예약(Overbooking)
  좌석 100개인 비행기에 110장 티켓 판매
  → 실제로 동시에 다 타는 경우는 드물기 때문에 가능
  → 하지만 모두가 다 타려 하면 문제 발생!
```

### requests + limits = 오버커밋 구현

```
컨테이너 A, B 각각:
  requests: 500MB (최소 보장)
  limits:   750MB (최대 사용 가능)

평소: A가 50MB만 쓰면 → B가 최대 750MB까지 사용 가능
위기: A가 500MB 필요해지면 → B에서 OOM(메모리 부족) 에러 발생
```

> ⚠️ **오버커밋의 트레이드오프**  
> 자원 활용률↑ ↔ OOM 발생 가능성↑  
> 자원을 더 효율적으로 쓸 수 있지만, 갑자기 죽을 수도 있다는 위험을 감수하는 것!

## ⚙️ 3. CPU vs 메모리 — 자원 종류에 따라 다르게 동작!

### CPU: “압축 가능한(Compressible) 자원”

CPU 경합이 생겨도 **컨테이너가 죽지 않습니다**. 대신 **쓰로틀링(Throttling)** 이 발생합니다.

```
CPU 쓰로틀링이란?
  → CPU 사용량을 강제로 줄이는 것 (느려지지만 죽지는 않음)
  → 마치 수도꼭지를 잠그는 것처럼 CPU를 조르는(throttle) 행위
```

**CPU 배분 방식 (CPU Shares)**:

- `requests.cpu`로 계산된 비율에 따라 CPU를 나눠 씁니다
- 유휴 CPU가 있으면 `requests.cpu` 비율대로 추가 분배

```
A: requests 500m, B: requests 500m
비율 = 1:1 → CPU 각 50%씩 사용
(C가 종료되어 유휴 CPU 생기면 비율에 맞게 재분배)
```

> 💡 **1000m = CPU 1코어?**  
> 엄밀히는 CPU 1코어를 **배타적으로** 쓰는 게 아닙니다.  
> 여러 물리 CPU 코어의 일부분을 모아서 1코어 성능처럼 사용하는 것입니다.  
> 성능이 중요하면 `CPU Manager` 기능으로 특정 코어를 독점할 수 있습니다.

---

### 메모리: “압축 불가능한(Non-compressible) 자원”

메모리는 CPU처럼 조금씩 줄일 수 없습니다. **경합이 발생하면 컨테이너를 종료**해서 메모리를 회수해야 합니다.

## 🚨 4. OOM Killer와 Eviction — 메모리 부족 시 대응

### 전체 흐름

```
메모리 부족 감지
       ↓
  [방법 1] kubelet이 감지 → Eviction (파드 통째로 이동)
       ↓ (kubelet이 감지 못하면)
  [방법 2] 리눅스 OOM Killer 작동 → 프로세스 강제 종료
```

### Eviction (퇴거) — kubelet이 담당

- `kubelet`(각 노드의 에이전트)이 주기적으로 노드 상태를 감시
- `MemoryPressure`, `DiskPressure` 등 임계치 초과 시 감지
- **파드를 통째로** 다른 노드로 이동시킴

### OOM Killer — 리눅스 커널이 담당

- kubelet보다 더 낮은 수준(커널 레벨)에서 동작
- 메모리 사용량과 우선순위를 계산해 **점수(oom_score)**가 높은 프로세스 강제 종료
- 파드 전체가 아닌 **프로세스 단위**로 종료 → 파드는 같은 노드에서 재시작 가능

|구분|OOM Killer|Eviction|
|---|---|---|
|**담당**|리눅스 커널|kubelet|
|**단위**|프로세스|파드 전체|
|**결과**|같은 노드에서 재시작|다른 노드로 이동|
|**속도**|즉각적|비교적 여유 있음|

## 🏷️ 5. QoS 클래스 — 종료 우선순위 결정

**어떤 파드를 먼저 종료할지** 결정하는 등급 시스템입니다. `limits`와 `requests` 설정에 따라 자동으로 부여됩니다.

### 🥇 Guaranteed (가장 안전)

**조건**: `requests == limits` (완전히 동일하게 설정)

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "128Mi"
  limits:
    cpu: "500m"      # requests와 동일!
    memory: "128Mi"  # requests와 동일!
```

> ✅ 가장 마지막에 종료됨 (가장 높은 보호)  
> ✅ `limits`만 설정해도 자동으로 `requests = limits`로 설정되어 Guaranteed 클래스가 됨  
> 🎯 주로 시스템 핵심 컴포넌트(kubelet, docker daemon 등)에 사용

---

### 🥈 Burstable (중간)

**조건**: `limits > requests` (오버커밋 상태)

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "64Mi"
  limits:
    cpu: "500m"      # limits > requests
    memory: "128Mi"  # limits > requests
```

> ⚠️ 메모리 부족 시 Guaranteed 다음으로 보호  
> ⚠️ 유휴 자원을 빌려 쓸 수 있지만, 자원 경합 시 종료될 수 있음  
> 🎯 일반적인 애플리케이션에 가장 많이 사용

---

### 🥉 BestEffort (가장 위험)

**조건**: `requests`와 `limits` 둘 다 **미설정**

```yaml
resources: {}  # 아무것도 설정 안 함
```

> ❌ 가장 먼저 종료됨  
> ✅ 유휴 자원을 마음껏 사용 가능  
> 🎯 중요하지 않은 배치 작업 등에 사용

---

### QoS 클래스 요약표

|QoS 클래스|조건|종료 우선순위|특징|
|---|---|---|---|
|**Guaranteed**|requests = limits|가장 마지막|안정적, 오버커밋 없음|
|**Burstable**|limits > requests|중간|유연하지만 위험 가능|
|**BestEffort**|둘 다 미설정|가장 먼저|무제한 사용 가능, 불안정|

## 🆕 6. Memory QoS — cgroup v2의 새로운 기능 (Kubernetes v1.22+)

> 📖 [쿠버네티스 공식 블로그](https://kubernetes.io/blog/2021/11/26/qos-memory-resources/) 내용

### 기존 문제점 (cgroup v1)

- CPU는 `requests`와 `limits` 모두 반영
- **메모리는 `requests`가 사실상 무시됨** → 스케줄링에만 사용, 실제 보호 없음
- 메모리는 throttling(압축) 불가 → 초과하면 즉시 OOM Kill

### cgroup v2로 해결!

**cgroup v2**는 메모리를 더 세밀하게 제어할 수 있는 새 버전입니다.

|cgroup 파라미터|역할|매핑|
|---|---|---|
|`memory.min`|절대 회수되지 않는 최소 보장 메모리|`requests.memory`|
|`memory.high`|이 값 초과 시 메모리 쓰로틀링 시작|`limits.memory × 0.8`|
|`memory.max`|하드 한도 (기존 방식과 동일)|`limits.memory`|

```
메모리 사용량 증가 →
  memory.min 이하: 커널이 절대 회수 안 함 (보장!)
  memory.high 초과: 쓰로틀링 시작 (서서히 제한)
  memory.max 초과: OOM Kill (즉시 종료)
```

### 기존 vs. Memory QoS 비교

```
【cgroup v1 기존 방식】
  0 ─────────────────────────[limit]── → OOM Kill
                                         (바로 죽음)

【cgroup v2 Memory QoS】
  0 ──[min]──────────[high]──[max]──
      ↑보장    ↑쓰로틀링 시작  ↑OOM Kill
                (미리 경고!)
```

> ✅ **핵심 개선**: 메모리도 CPU처럼 한 번에 죽지 않고, **점진적으로 제어**할 수 있게 됨!

### 사용 조건

|조건|최소 버전|
|---|---|
|Kubernetes|v1.22 이상|
|Linux 커널|4.15 이상 (5.2+ 권장)|
|컨테이너 런타임|containerd 1.4+ / cri-o 1.20+|
|cgroup v2|활성화 필요|

## 🎯 최종 정리

```
파드 리소스 관리 핵심 3원칙

1️⃣  requests  → 스케줄링 기준 + 최소 보장량
2️⃣  limits    → 절대 최대 사용량
3️⃣  requests < limits → 오버커밋 (자원 효율↑, 위험↑)

CPU  → 경합 시: 쓰로틀링 (느려지지만 안 죽음)
메모리 → 경합 시: OOM Kill 또는 Eviction (종료!)

QoS 클래스 (종료 순서)
  BestEffort → Burstable → Guaranteed
  (먼저 죽음)              (마지막에 죽음)
```

> 💡 **실무 팁**: 프로덕션 환경에서는 반드시 `requests`와 `limits`를 설정하세요.  
> 설정하지 않으면 BestEffort 클래스가 되어 메모리 부족 시 가장 먼저 종료됩니다!
