# ArgoCD 완벽 가이드: 초보자를 위한 GitOps 입문

ArgoCD를 처음 접하는 분들을 위해, 기초 개념부터 실무 활용까지 차근차근 설명해 드릴게요.

---

## 1. ArgoCD가 뭔가요?

**ArgoCD**는 Kubernetes를 위한 **GitOps 기반 지속적 배포(CD) 도구**입니다.

### 핵심 개념: GitOps란?

GitOps는 **"Git 저장소를 단일 진실의 원천(Single Source of Truth)으로 사용"**하는 운영 방식입니다.

```
전통적인 배포 방식:
개발자 → 빌드 → 수동 배포 명령 → 서버에 적용

GitOps 방식:
개발자 → Git에 Push → ArgoCD가 감지 → 자동으로 K8s에 적용
```

### ArgoCD의 핵심 철학

|원칙|설명|
|---|---|
|**선언적(Declarative)**|"어떻게"가 아닌 "무엇을" 원하는지 정의|
|**버전 관리**|모든 변경사항이 Git에 기록됨|
|**자동 동기화**|Git과 클러스터 상태를 자동으로 일치시킴|
|**감사 추적**|누가, 언제, 무엇을 변경했는지 추적 가능|

---

## 2. 왜 ArgoCD를 사용하나요?

### 기존 방식의 문제점

```bash
# 전통적인 배포 (문제가 많음)
kubectl apply -f deployment.yaml  # 누가 언제 실행했지?
kubectl set image deployment/app app=myapp:v2  # 이 변경이 어디에 기록되지?
```

**문제점:**

- 누가 어떤 변경을 했는지 추적 어려움
- 실수로 잘못된 버전 배포 시 롤백이 복잡
- 여러 환경(개발/스테이징/프로덕션) 관리가 힘듦

### ArgoCD를 사용하면

```yaml
# Git에 저장된 deployment.yaml만 수정하면 끝!
# ArgoCD가 자동으로 변경 감지 → 클러스터에 적용
```

**장점:**

- ✅ 모든 변경이 Git에 기록 (감사 추적)
- ✅ PR 리뷰를 통한 배포 승인
- ✅ 롤백 = Git revert (매우 간단)
- ✅ 환경별 설정 관리 용이

## 4. 실무에서의 Git 저장소 구조

### 일반적인 저장소 분리 전략

실무에서는 보통 **두 개의 Git 저장소**를 사용합니다:

```
┌─────────────────────────────────────────────────────────────────┐
│                    실무 Git 저장소 구조                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ┌───────────────────────┐      ┌───────────────────────────┐   │
│  │  Application Repo     │      │  GitOps/Config Repo       │   │
│  │  (소스코드 저장소)     │      │  (배포 설정 저장소)         │   │
│  ├───────────────────────┤      ├───────────────────────────┤   │
│  │                       │      │                           │   │
│  │  my-app/              │      │  k8s-configs/             │   │
│  │  ├── src/             │      │  ├── base/                │   │
│  │  │   └── main.py      │      │  │   ├── deployment.yaml  │   │
│  │  ├── Dockerfile       │      │  │   ├── service.yaml     │   │
│  │  ├── tests/           │      │  │   └── kustomization.yaml│  │
│  │  └── README.md        │      │  ├── overlays/            │   │
│  │                       │      │  │   ├── dev/             │   │
│  │                       │      │  │   ├── staging/         │   │
│  │                       │      │  │   └── prod/            │   │
│  │                       │      │  └── applications/        │   │
│  │                       │      │      └── my-app.yaml      │   │
│  └───────────────────────┘      └───────────────────────────┘   │
│            │                               ▲                     │
│            │  CI에서 이미지 태그 업데이트    │                     │
│            └───────────────────────────────┘                     │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 왜 저장소를 분리하나요?

1. **관심사 분리**: 애플리케이션 개발자와 인프라 담당자의 영역 분리
2. **보안**: 인프라 설정은 별도 권한으로 관리
3. **배포 독립성**: 코드 변경 없이 설정만 변경 가능

## 5. 실제 설정 예시

### GitOps 저장소 구조

```bash
k8s-configs/
├── applications/           # ArgoCD Application 정의
│   ├── my-api.yaml
│   └── my-frontend.yaml
├── base/                   # 공통 리소스 정의
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── configmap.yaml
│   └── kustomization.yaml
└── overlays/               # 환경별 설정
    ├── dev/
    │   ├── kustomization.yaml
    │   └── replica-patch.yaml
    ├── staging/
    │   ├── kustomization.yaml
    │   └── replica-patch.yaml
    └── prod/
        ├── kustomization.yaml
        ├── replica-patch.yaml
        └── ingress-patch.yaml
```

### base/deployment.yaml (기본 배포 설정)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-api
spec:
  replicas: 1  # 기본값, overlay에서 환경별로 변경
  selector:
    matchLabels:
      app: my-api
  template:
    metadata:
      labels:
        app: my-api
    spec:
      containers:
      - name: my-api
        image: myregistry/my-api:latest  # CI에서 자동 업데이트
        ports:
        - containerPort: 8080
        resources:
          requests:
            memory: "128Mi"
            cpu: "100m"
          limits:
            memory: "256Mi"
            cpu: "200m"
```

### overlays/prod/kustomization.yaml (프로덕션 설정)

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: production

resources:
  - ../../base

# 프로덕션용 패치
patches:
  - path: replica-patch.yaml

# 프로덕션용 ConfigMap 값
configMapGenerator:
  - name: my-api-config
    behavior: merge
    literals:
      - LOG_LEVEL=warn
      - ENVIRONMENT=production
```

### overlays/prod/replica-patch.yaml

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-api
spec:
  replicas: 5  # 프로덕션은 5개 레플리카
```

### ArgoCD Application 정의

```yaml
# applications/my-api.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-api-prod
  namespace: argocd
spec:
  project: default
  
  # 소스: Git 저장소
  source:
    repoURL: https://github.com/mycompany/k8s-configs.git
    targetRevision: main
    path: overlays/prod
  
  # 대상: Kubernetes 클러스터
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  
  # 동기화 정책
  syncPolicy:
    automated:
      prune: true      # Git에서 삭제된 리소스도 클러스터에서 삭제
      selfHeal: true   # 수동 변경을 자동으로 원복
    syncOptions:
      - CreateNamespace=true
```

### GitHub Actions CI 예시

```yaml
# .github/workflows/ci-cd.yaml (Application Repo에 위치)
name: CI/CD Pipeline

on:
  push:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}
    
    steps:
      # 1. 코드 체크아웃
      - name: Checkout
        uses: actions/checkout@v4
      
      # 2. 테스트 실행
      - name: Run tests
        run: |
          pip install -r requirements.txt
          pytest tests/
      
      # 3. Docker 이미지 빌드 & 푸시
      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}

  update-gitops:
    needs: build-and-push
    runs-on: ubuntu-latest
    
    steps:
      # GitOps 저장소 체크아웃
      - name: Checkout GitOps repo
        uses: actions/checkout@v4
        with:
          repository: mycompany/k8s-configs
          token: ${{ secrets.GITOPS_TOKEN }}
          path: gitops
      
      # 이미지 태그 업데이트
      - name: Update image tag
        run: |
          cd gitops/overlays/prod
          kustomize edit set image myregistry/my-api=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
      
      # GitOps 저장소에 커밋 & 푸시
      - name: Commit and push
        run: |
          cd gitops
          git config user.name "GitHub Actions"
          git config user.email "actions@github.com"
          git add .
          git commit -m "Update my-api to ${{ github.sha }}"
          git push
```

## 7. ArgoCD 주요 기능 & CLI 명령어

### Application 상태 확인

```bash
# 모든 애플리케이션 목록
argocd app list

# 특정 앱 상태 확인
argocd app get my-api-prod

# 출력 예시:
# Name:               my-api-prod
# Server:             https://kubernetes.default.svc
# Namespace:          production
# Sync Status:        Synced
# Health Status:      Healthy
```

### 수동 동기화

```bash
# Git과 동기화 실행
argocd app sync my-api-prod

# 강제 동기화 (충돌 무시)
argocd app sync my-api-prod --force
```

### 롤백

```bash
# 배포 이력 확인
argocd app history my-api-prod

# 특정 버전으로 롤백
argocd app rollback my-api-prod <revision-id>
```

## 8. 동기화 전략 이해하기

### Auto Sync vs Manual Sync

```yaml
# 자동 동기화 (권장: 개발/스테이징 환경)
syncPolicy:
  automated:
    prune: true      # Git에서 삭제된 리소스 자동 삭제
    selfHeal: true   # kubectl로 수동 변경 시 자동 원복
    allowEmpty: false

# 수동 동기화 (권장: 프로덕션 환경)
syncPolicy: {}  # 또는 생략
```

### Sync Waves (배포 순서 제어)

여러 리소스를 순서대로 배포해야 할 때:

```yaml
# 1단계: ConfigMap 먼저 배포
apiVersion: v1
kind: ConfigMap
metadata:
  name: my-config
  annotations:
    argocd.argoproj.io/sync-wave: "-1"  # 음수 = 먼저 배포
---
# 2단계: Deployment 배포
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-api
  annotations:
    argocd.argoproj.io/sync-wave: "0"   # 기본값
---
# 3단계: 배포 후 작업 (예: DB 마이그레이션)
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  annotations:
    argocd.argoproj.io/sync-wave: "1"   # 양수 = 나중에 실행
    argocd.argoproj.io/hook: PostSync   # Sync 완료 후 실행
```

## 9. 실무 베스트 프랙티스

### ✅ DO (권장사항)

|항목|설명|
|---|---|
|**저장소 분리**|애플리케이션 코드와 GitOps 설정 분리|
|**환경별 브랜치/디렉토리**|`overlays/dev`, `overlays/prod` 사용|
|**PR 기반 배포**|프로덕션 변경은 반드시 PR 리뷰|
|**Sealed Secrets**|시크릿은 암호화하여 Git에 저장|
|**Health Check 정의**|커스텀 헬스체크로 배포 상태 정확히 파악|

### ❌ DON'T (피해야 할 것)

|항목|이유|
|---|---|
|**kubectl 직접 사용**|ArgoCD가 변경을 원복시킴 (selfHeal)|
|**Plain Secret 커밋**|보안 위험! Sealed Secrets 사용|
|**자동 동기화만 사용**|프로덕션은 수동 승인 권장|
|**하나의 큰 Application**|마이크로서비스별로 분리|

## 10. 트러블슈팅 가이드

### 자주 발생하는 문제들

**문제 1: OutOfSync 상태가 해결되지 않음**

```bash
# 상세 diff 확인
argocd app diff my-api-prod

# 강제 동기화
argocd app sync my-api-prod --force --prune
```

**문제 2: 이미지 Pull 실패**

```yaml
# imagePullSecrets 설정 확인
spec:
  template:
    spec:
      imagePullSecrets:
        - name: registry-credentials
```

**문제 3: Health 상태가 Degraded**

```bash
# Pod 상태 확인
kubectl get pods -n production

# Pod 로그 확인
kubectl logs -n production <pod-name>

# ArgoCD 리소스 트리 확인
argocd app resources my-api-prod
```

## 요약: ArgoCD로 얻는 것

```
┌──────────────────────────────────────────────────────────────┐
│                    ArgoCD 도입 전/후 비교                     │
├────────────────────────┬─────────────────────────────────────┤
│        도입 전          │            도입 후                  │
├────────────────────────┼─────────────────────────────────────┤
│ kubectl apply 수동 실행 │ Git push만 하면 자동 배포          │
│ 변경 이력 추적 어려움   │ 모든 변경이 Git에 기록             │
│ 롤백 복잡              │ git revert로 간단히 롤백            │
│ 환경별 설정 관리 힘듦   │ Kustomize/Helm으로 체계적 관리     │
│ 누가 뭘 했는지 모름    │ PR 리뷰 + Git 커밋 기록으로 명확   │
│ 클러스터 상태 불확실    │ UI/CLI로 실시간 상태 모니터링      │
└────────────────────────┴─────────────────────────────────────┘
```
