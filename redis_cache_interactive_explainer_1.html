Cache Hit 읽기 요청 성공

1
Client → API Pod
GET /products/123 요청 전송
2
API Pod → Redis
캐시 키 "product:123" 조회
3
Redis → API Pod → Client
데이터 존재! 즉시 반환 (1~5ms)
GET product:123 → "{"id":123,"name":"상품A"}" → 응답시간: ~3ms ✓

Cache Miss 읽기 요청 실패 → DB 조회

1
Client → API Pod
GET /products/456 요청 전송
2
API Pod → Redis
캐시 키 "product:456" 조회 → NULL (Miss!)
3
API Pod → RDS Read Replica
SELECT * FROM products WHERE id = 456
4
API Pod → Redis
SETEX product:456 3600 "{...}" (TTL 1시간으로 캐싱)
5
API Pod → Client
데이터 반환 (30~50ms)
GET product:456 → NULL (Miss) → SELECT * FROM products WHERE id=456 → SETEX product:456 3600 "{...}" → 응답시간: ~45ms (다음 요청은 ~3ms)

Write 쓰기 요청 + 캐시 무효화

1
Client → API Pod
PUT /products/123 (상품 정보 수정)
2
API Pod → RDS Primary
UPDATE products SET name='상품B' WHERE id=123
3
API Pod → Redis
DEL product:123 (캐시 무효화로 stale 데이터 방지)
4
다음 읽기 요청
Cache Miss → 최신 데이터 DB에서 조회 후 재캐싱
UPDATE products SET name='상품B' WHERE id=123 → DEL product:123 (무효화) → 다음 GET: Miss → 최신 데이터 캐싱
1. Cache-Aside 현재 적용
App이 캐시와 DB를 직접 제어
2. Read-Through
캐시가 DB 조회 로직을 캡슐화
3. Write-Through
캐시+DB 동시 쓰기 (동기)
4. Write-Behind
캐시만 쓰고 DB는 비동기
