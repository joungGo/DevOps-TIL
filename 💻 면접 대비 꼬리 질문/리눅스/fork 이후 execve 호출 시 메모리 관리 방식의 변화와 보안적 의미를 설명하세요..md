### 답변
`fork()` 이후에는 부모와 자식이 COW 기반으로 동일한 주소 공간을 공유합니다.  
즉, 페이지 테이블은 복사되지만 물리 메모리는 공유되고, 쓰기 시점에만 복사가 발생합니다.

하지만 `execve()`가 호출되면 상황이 완전히 달라집니다.

첫째, 기존 주소 공간이 전부 제거됩니다.  
커널은 자식 프로세스의 코드, 데이터, 힙, 스택 영역을 모두 해제하고  
새로운 실행 파일을 로드합니다.

둘째, 새로운 페이지 테이블 구성이 이루어집니다.  
실행 파일의 코드 영역은 읽기 전용으로 매핑되고,  
데이터와 스택은 새로 할당됩니다.  
즉, COW로 공유하던 부모의 메모리와는 완전히 분리됩니다.

셋째, 보안적 의미입니다.

- 이전 프로세스 메모리가 완전히 제거되므로  
    민감 정보가 새 프로그램에 노출되지 않습니다.

### 꼬리질문: 새로운 페이지 테이블이 구성될 때 세그먼트와 페이지의 차이점은 무엇인가요?
새로운 페이지 테이블이 구성될 때,  
세그먼트와 페이지는 역할과 단위가 다릅니다.

먼저, **세그먼트**는 논리적 구분입니다.  
코드, 데이터, 힙, 스택처럼 프로그램의 의미 단위로 나뉩니다.  
각 세그먼트는 접근 권한과 용도가 다릅니다.

반면, **페이지**는 물리 메모리 관리 단위입니다.  
보통 4KB 고정 크기로 나뉘며,  
실제 매핑과 보호는 페이지 단위로 이루어집니다.

`execve()` 시 커널은  
먼저 실행 파일을 기준으로 코드/데이터 같은 세그먼트를 정의하고,  
그 다음 이를 **페이지 단위로 나누어 페이지 테이블에 매핑**합니다.

즉,

- 세그먼트: 논리적 구조, 권한과 의미 중심
    
- 페이지: 물리적 관리 단위, MMU가 처리하는 최소 단위
    

정리하면,  
세그먼트는 프로그램 관점의 구분이고,  
페이지는 하드웨어 기반 메모리 관리 단위입니다.

### 꼬리질문 : 페이지 테이블의 Hierarchical Paging 구조와 Inverted Page Table의 차이점은 무엇인가요?
두 방식의 핵심 차이는 **페이지 테이블을 어떤 기준으로 구성하느냐**입니다.

먼저, **Hierarchical Paging(다단계 페이지 테이블)**입니다.

- 각 프로세스가 **자기만의 페이지 테이블**을 가집니다.
    
- 가상 주소를 여러 단계로 나누어, 단계별 테이블을 따라가며 물리 프레임을 찾습니다.
    
- 사용하지 않는 영역은 테이블을 생성하지 않기 때문에 메모리 낭비를 줄일 수 있습니다.
    

장점은 구현이 직관적이고, 가상 주소 기반 조회가 빠르다는 점입니다.  
단점은 프로세스 수가 많아지면 페이지 테이블 자체의 메모리 사용량이 커진다는 점입니다.

반면, **Inverted Page Table**은 구조가 반대입니다.

- 시스템 전체에 **하나의 페이지 테이블만 존재**합니다.
    
- 물리 프레임 수만큼 엔트리가 있고,  
    각 엔트리는 “이 물리 프레임이 어떤 (프로세스, 가상 페이지)을 매핑하는지”를 기록합니다.
    

즉,  
Hierarchical은 “가상 주소 → 물리 프레임” 기준이고,  
Inverted는 “물리 프레임 → (프로세스, 가상 주소)” 기준입니다.

장점은 물리 메모리 크기에 비례하므로  
프로세스 수가 많아도 테이블 크기가 크게 증가하지 않는다는 점입니다.

단점은 가상 주소에서 바로 인덱싱이 어렵기 때문에  
해시 기반 검색이 필요하고, 조회 비용이 더 들 수 있습니다.

정리하면,

- Hierarchical Paging: 프로세스별 테이블, 가상 주소 중심 구조
    
- Inverted Page Table: 시스템 전체 단일 테이블, 물리 메모리 중심 구조
    

즉, 메모리 사용량 확장성 측면에서 접근 방식이 다르다고 설명할 수 있습니다.

---
### 꼬리질문: Translation Lookaside Buffer(TLB)는 무엇이고, 페이지 테이블 조회 시 TLB의 역할은 무엇인가요?
TLB는 **Translation Lookaside Buffer**의 약자로,  
가상 주소 → 물리 주소 변환 결과를 캐시하는 **MMU 내부의 고속 캐시**입니다.

페이지 테이블 조회는 기본적으로 메모리를 여러 번 접근해야 하는 비용이 큰 작업입니다.  
특히 다단계 페이지 테이블에서는 단계마다 메모리 접근이 필요합니다.

TLB의 역할은 이 변환 결과를 미리 저장해 두는 것입니다.

동작 흐름은 다음과 같습니다.

1. CPU가 가상 주소로 메모리 접근을 시도합니다.
    
2. 먼저 TLB에서 해당 가상 페이지 번호를 검색합니다.
    
3. TLB hit이면, 저장된 물리 프레임 번호를 바로 사용합니다.  
    → 페이지 테이블 접근 없이 즉시 변환됩니다.
    
4. TLB miss이면,  
    → 페이지 테이블을 따라가며 물리 주소를 찾고  
    → 그 결과를 TLB에 저장합니다.
    

즉, TLB는 페이지 테이블 접근을 줄여  
주소 변환 지연을 크게 줄이는 역할을 합니다.

정리하면,  
TLB는 가상 메모리 시스템의 성능을 좌우하는 핵심 캐시이며,  
페이지 테이블 조회 비용을 상쇄하기 위한 하드웨어 최적화 장치입니다.

---
### 꼬리질문: TLB에 대한 캐시 미스가 발생했을 때, 이를 해결하기 위한 대표적인 방법은 무엇이 있고, 이 방법들의 장단점은 무엇인가요?
TLB miss가 발생하면 기본적으로 두 가지 방식으로 처리합니다.

첫째, **하드웨어 기반 Page Walk**입니다.  
MMU가 직접 다단계 페이지 테이블을 따라가 물리 주소를 찾습니다.  
현대 x86 아키텍처가 이 방식을 사용합니다.

장점은 소프트웨어 개입이 없어서 빠르고, 구현이 단순하다는 점입니다.  
단점은 페이지 테이블 구조가 하드웨어에 종속되고, 유연성이 떨어진다는 점입니다.

둘째, **소프트웨어 기반 TLB 처리**입니다.  
TLB miss가 발생하면 예외를 발생시키고,  
커널이 직접 페이지 테이블을 탐색해 TLB를 채웁니다.  
MIPS 같은 구조에서 사용됩니다.

장점은 페이지 테이블 구조를 OS가 자유롭게 설계할 수 있다는 점입니다.  
단점은 예외 처리 비용이 커서 miss 시 오버헤드가 크다는 점입니다.

추가적으로 miss 자체를 줄이기 위한 방법도 있습니다.

- **Huge Page 사용**: 페이지 크기를 키워 TLB 엔트리당 커버 범위를 확장  
    → TLB miss 감소  
    → 단점은 메모리 단편화 증가
    
- **TLB 용량 증가 및 다단계 TLB 구조**  
    → miss율 감소  
    → 하드웨어 비용 증가
    

정리하면,  
TLB miss 해결은

1. miss 발생 시 처리 전략과
    
2. miss 자체를 줄이는 전략  
    두 관점으로 나눌 수 있으며,  
    성능과 유연성 사이의 트레이드오프가 존재합니다.

### 꼬리질문: 하드웨어 기반 Page Walk와 소프트웨어 기반 TLB 처리 중에서 어떤 상황에서 어떤 방식을 선택하는 것이 좋을지에 대해 어떻게 생각하시나요?
선택 기준은 **성능 최적화 중심인지, OS 유연성 중심인지**에 따라 달라진다고 생각합니다.

먼저, **일반적인 범용 서버나 데스크탑 환경**에서는  
하드웨어 기반 Page Walk가 적합합니다.  
TLB miss가 발생해도 MMU가 자동으로 처리하기 때문에  
예외 처리 오버헤드가 없고 평균 지연이 안정적입니다.  
대부분의 x86 기반 리눅스 서버가 이 구조를 사용합니다.

반면, **임베디드 시스템이나 특수 목적 OS**에서는  
소프트웨어 기반 TLB 처리가 유리할 수 있습니다.  
OS가 직접 TLB miss를 처리하므로  
페이지 테이블 구조를 자유롭게 설계할 수 있고,  
특정 워크로드에 맞게 최적화가 가능합니다.

다만, 이 방식은 miss 발생 시 트랩 비용이 크기 때문에  
실시간성이 매우 중요한 환경에서는 신중해야 합니다.
